## Overview

Once we land a foothold on a Windows host, the fastest route to higher privilege and lateral movement is usually **credentials that are already sitting on the machine** — not an exploit. Administrators, developers, and ordinary users constantly leave passwords in config files, scripts, saved sessions, and browsers. The job is to systematically search the places Windows and its applications stash secrets.

Think of credential hunting as:

> "Reading the machine's mind for everything it already remembers how to log into."

The same principle as Linux applies: understand *what a service is and who uses it*, because a password tied to a database, a service account, or a domain admin is far more valuable than a personal app login.

---

## Where credentials live on Windows

There are four broad sources to sweep, mirroring the Linux approach:

| Source | Examples |
|--------|----------|
| **Files** | configs (`web.config`, `*.ini`, `*.xml`), scripts (`*.ps1`, `*.bat`, `*.vbs`), notes (`*.txt`), unattended-install files |
| **History** | PowerShell console history, RDP connection history |
| **Memory** | LSASS (covered in the LSASS section), running processes |
| **Stores / vaults** | Credential Manager, browser password stores, KeePass/password managers, sticky notes |

<Tip>
**Always start broad with an automated tool, then narrow with targeted searches based on what services/apps you saw during enumeration.**

</Tip>

## Searching files with findstr & dir

`findstr` is the Windows equivalent of `grep`. The classic recursive search for the word "password" across common config/script types:

```cmd
findstr /SIM /C:"password" *.txt *.ini *.config *.xml *.ps1 *.bat *.cmd *.vbs
```

- `/S` recurse subdirectories, `/I` case-insensitive, `/M` print only the filename, `/C:"..."` literal search string.

Hunt by **filename** for the usual suspects:

```cmd
dir /s /b *pass* *cred* *vnc* *.config* 2>nul
where /r C:\ *.kdbx
```

<Info>
**Why these matter**

Apps store their settings (often including a DB or service password) in `.config`/`.ini`/`.xml`. KeePass databases (`.kdbx`) are jackpots — crack them with `keepass2john` (see the *Cracking Protected Files* section).
</Info>

## High-value Windows locations

These specific spots pay off again and again — know *why* each one holds secrets:

- **Unattended install files** — used to auto-deploy Windows; frequently contain a local admin password (sometimes base64-encoded):
  ```cmd
  C:\Windows\Panther\Unattend.xml
  C:\Windows\Panther\Autounattend.xml
  C:\Windows\System32\Sysprep\unattend.xml
  ```
- **PowerShell history** — users paste creds straight into commands; the console logs them per-user:
  ```cmd
  type %APPDATA%\Microsoft\Windows\PowerShell\PSReadline\ConsoleHost_history.txt
  ```
- **IIS / web app configs** — `web.config` holds DB connection strings with `user`/`password`:
  ```cmd
  dir /s /b C:\inetpub\web.config
  ```
- **Saved RDP / generic creds** — Credential Manager (see the dedicated *Windows Credential Manager* section):
  ```cmd
  cmdkey /list
  runas /savecred /user:DOMAIN\user cmd
  ```
- **Autologon in the registry** — a plaintext password if autologon is enabled:
  ```cmd
  reg query "HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon" /v DefaultPassword
  ```
- **Sticky Notes** — people literally write passwords here:
  ```
  %LocalAppData%\Packages\Microsoft.MicrosoftStickyNotes_*\LocalState\plum.sqlite
  ```

<Info>
**Worked example — what a "find" looks like**

Hunting through configs and an app's auth files on one box turned up a database connection string and a small web-app user list:
```text
URL:  mysql://localhost:3306/mydatabase
user: bd_user
pass: +mQwYxIFaEjZ/MWJDkm1SCWhHw7xPXWd

loginUrl = "login.aspx"
user1:password1
user2:password2
```
A DB credential like this is high-value: try it against the database directly, and — because of password reuse — against SMB/RDP/WinRM and any domain account with the same username.
</Info>

## Automated tools

### LaZagne (the go-to)

LaZagne pulls stored credentials from dozens of Windows apps (browsers, mail clients, Wi-Fi, databases, sysadmin tools) in one run:

```cmd
LaZagne.exe all
LaZagne.exe browsers      # only browser-stored creds
```

<Info>
**Why it works**

Apps store "saved" passwords encrypted with keys the **logged-in user** can access (often via DPAPI). Running as that user, LaZagne simply asks the same APIs to decrypt them — no cracking needed.
</Info>

### Other useful tools

- **SessionGopher** — extracts saved session info from PuTTY, WinSCP, FileZilla, RDP (`.rdp`), and VNC.
- **SharpDPAPI / DonPAPI** — decrypt DPAPI-protected blobs (browser creds, Credential Manager, vaults).
- **Windows Search** — the GUI search itself can find files containing keywords if indexing is on.

---

## Browser credentials

Browsers save passwords encrypted **per-user** (Chrome/Edge via DPAPI + AES, Firefox via its own key store). Because the encryption is tied to the user profile, anything running as that user can decrypt them:

```cmd
LaZagne.exe browsers
```

- Chrome/Edge store them in `Login Data` (a SQLite DB) under the user's `AppData\Local`.
- Firefox uses `logins.json` + `key4.db` in the profile folder — decrypt with `firefox_decrypt.py` if you exfiltrate them.

## Key Takeaways

- On a Windows foothold, **hunt credentials first** — it's usually faster than exploiting and feeds both privesc and lateral movement.
- Sweep four sources: **files**, **history**, **memory (LSASS)**, and **stores/vaults** (Credential Manager, browsers, KeePass).
- `findstr /SIM /C:"password" ...` and `dir /s /b *pass*` are your manual workhorses; `LaZagne.exe all` is the automated sweep.
- Highest-value spots: **unattend.xml**, **PowerShell history**, **web.config**, **Credential Manager**, **registry autologon**, and **browser stores**.
- A recovered credential is a pivot — **reuse it** across services and accounts (password reuse is rampant), and crack any `.kdbx`/DPAPI blobs you find offline.
