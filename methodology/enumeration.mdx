## The enumeration loop

1. **Observe:** record what you can actually see, including the host, service, session, or account that produced it.
2. **Explain:** write one possible reason for the observation. Keep this separate from facts.
3. **Check:** choose one small comparison that would support or weaken that explanation.
4. **Record:** save the request or command, relevant result, and what changed. Preserve a normal baseline.
5. **Branch:** continue only when the result supports the hypothesis. Otherwise record the limit and return to the inventory.
6. **Repeat after access changes:** a new account, hostname, readable file, local privilege, or network route changes what you can enumerate.

For example: “the application has a language parameter” is an observation; “it includes a server-side file” is a hypothesis. Comparing valid and invalid values and recording path-handling behavior is the next check. It is not yet a finding of code execution.

## First ten minutes

- Write the lab objective and the supplied hostnames, addresses, and credentials.
- Identify your current location and identity: workstation, pivot, browser session, local user, or domain user.
- Create an inventory before committing to a technique. Follow the relevant subject guide above.
- For every promising lead, write **what I control → what processes it → what I can observe**.
- Keep an “untested” list. An unexplored service is different from a tested service that yielded no lead.

## A reusable evidence sheet

| Field | What to record |
| --- | --- |
| Location and identity | Host, network vantage point, account, session |
| Observation | Exact feature, response, file, membership, or permission |
| Hypothesis | What might explain the observation |
| Prerequisites | What must be true for the next technique to work |
| Smallest useful check | One changed input or one permission/reachability check |
| Result | Evidence saved; confirmed, contradicted, or inconclusive |
| Next action | Follow the result or name the missing information |

## When nothing works

First classify the failure: **reachability, naming, authentication, authorization, syntax/context, or hypothesis**. A tool failure does not tell you which one failed. Check the simplest layer first: correct host and port, correct name, live session, accepted identity, then rights and technique prerequisites.

Return to enumeration when you cannot explain why a payload or command should work. Repeatedly changing tools without a new observation usually leaves the same gap. Review another service, another application role, overlooked source/configuration files, or an untested host name.
