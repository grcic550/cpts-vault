**Requires:** WinRM access and an authorized account. Prefer the host FQDN with working domain DNS; an IP address may require a different trust/authentication setup.

## Check and connect

**Windows PowerShell**

```powershell
Test-WSMan HOST_FQDN
Enter-PSSession -ComputerName HOST_FQDN -Credential DOMAIN\USER
```

## Run a command

**Windows PowerShell**

```powershell
Invoke-Command -ComputerName HOST_FQDN -Credential DOMAIN\USER -ScriptBlock { whoami }
```

### Find Credentials in Network Shares

**Find Credentials in Network Shares**

```bash
# the domain prefix (most reliable signal)
grep -ri "DOMAINNAME\\\\" .

# UPN format
grep -riE "[a-z]+@domain\.local" .

# runas / net use / Invoke-Command patterns - operators leak creds in commands
grep -riE "runas|net use|Invoke-Command|New-PSSession|ConvertTo-SecureString" .

# anything with "service account" / "svc_" in filenames
find . -iname "*svc*" -o -iname "*service*account*"
```


**Pass the Ticket from Windows**

Context from the notebook: Launching  powershell  from that same  cmd.exe   inherits the ticket , so  Enter-PSSession -ComputerName DC01  authenticates over  WinRM with Kerberos  as the ticket owner — landing you on the DC as  john .

<Accordion title="Where it fits in a pentest">

### Where it fits in a pentest

**Pass the Ticket from Windows**

Context from the notebook: PtT is core  lateral movement  in an AD engagement. Typical chain: land on a box →  sekurlsa::ekeys / tickets  or  Rubeus dump  → grab a privileged user's TGT (or  asktgt  from their key) → inject →  Enter-PSSession / impacket  to the next host or the DC. It's preferred over PtH when the environment is Kerberos-only or you want to stay AES-native and quieter. It also chains from other attacks that  yield  tickets: Kerberoasting, AS-REP roasting, unconstrained delegation, and  Pass the Certificate  (PKINIT → TGT).

```text
Enter-PSSession
```
