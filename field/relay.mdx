## Prove the authentication source and destination independently

NTLM relay uses a live authentication exchange against another service. Capturing a challenge/response for offline password recovery is a separate process. Build a small diagram naming the authenticating client/account, your receiving listener and the destination protocol/host.

### Inspect the destination first

```bash
nmap -Pn -p 445 --script smb2-security-mode TARGET_IP
nxc smb TARGET_IP
```

Required SMB signing blocks the usual relay path to that SMB destination. LDAP signing/channel binding and HTTP extended protection concern other destinations; one service's setting does not establish another's behavior. Verify that the relayed identity has useful rights on the intended service.

### Confirm listener and target configuration

```bash
ss -lntup
impacket-ntlmrelayx -h
```

Resolve port conflicts before running a receiving service. If combining a name-resolution listener with a relay component in a lab, configure their responsibilities explicitly so they do not compete for the same address/port. Choose the destination from observed evidence rather than passing an unreviewed list of every host.

### Interpret the exchange by stage

| Stage | Evidence to preserve |
| --- | --- |
| Incoming authentication | Client address, account/domain, protocol and timestamp |
| Destination connection | Actual destination host/port and negotiated service |
| Authentication result | Accepted/rejected exchange and protection-related errors |
| Authorized action | The specific resource or operation the identity can access |
| Returned artifact | Session, ticket, certificate or command result with its identity |

An incoming connection with no useful result can mean the destination is protected, the exchange is incompatible, or the identity lacks the necessary rights. Repeatedly changing listeners will not fix a destination authorization problem.

Use the worked relay/certificate recipes below only after those prerequisites match. Preserve exact tool versions and configuration with the result; protocol protections and server patches can invalidate assumptions from older lab material. End the test by stopping the listeners and restoring any configuration changed for the exercise.

## Kali — inspect the SMB destination

```bash
nmap -Pn -p 445 --script smb2-security-mode TARGET_IP
```

Read whether signing is **required**, not simply supported. A destination requiring SMB signing blocks the usual SMB relay path to that destination.

## Before starting a listener

| Need | Verify |
| --- | --- |
| Incoming authentication | Which lab system will authenticate, with which account, and over which protocol? |
| Reachable destination | The relay host must reach the destination service. |
| Eligible protocol | SMB signing, LDAP signing/channel binding, and HTTP extended protection are different controls. |
| Useful account rights | Relayed authentication does not add privileges the account lacks. |
| Free listening port | Two tools cannot both own the same address and port. |

Open [ntlmrelayx commands](/commands/ntlmrelayx) or the saved [AD CS certificate lab](/password-attacks/pass-the-certificate). Collecting a NetNTLM response for offline cracking and relaying an authentication exchange are separate techniques.

If you receive authentication but no useful session, check the destination protection and authorization before assuming the listener is broken.
