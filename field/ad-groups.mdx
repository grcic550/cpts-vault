## Prove a membership chain and its effect

Start with the account and the specific resource you want to access. A useful group finding identifies the object SID, direct and nested membership, the permission granted to that group, and whether the current session can use it.

```powershell
Import-Module ActiveDirectory
Get-ADUser student -Properties MemberOf,PrimaryGroupID,SID
Get-ADPrincipalGroupMembership student | Select-Object Name,GroupScope,GroupCategory,SID
Get-ADGroup 'Helpdesk' -Properties MemberOf,Members,GroupCategory,GroupScope,SID
Get-ADGroupMember 'Helpdesk'
Get-ADGroupMember 'Helpdesk' -Recursive
```

Use your actual account/group names. MemberOf alone is not a complete effective-access calculation; retain the primary-group information and investigate the relevant nesting. Compare direct and recursive results: save intermediate groups separately when explaining the chain. Querying membership is not changing membership.

### Compare the directory with the session

```powershell
whoami /user
whoami /groups
Get-LocalGroup
Get-LocalGroupMember -Group 'Administrators'
```

The LocalAccounts commands run on the resource host and require the module; group names can be localized. A domain group and a local group are different objects. A recently changed directory membership may not appear in an existing token. Inspect enabled/deny-only state and logon context before claiming the permission is usable.

### Verify the exact permission

For a file/share lead, connect with the same identity and inspect that resource. For an AD object, resolve its ACL trustee SID, inherited rights, object-specific permissions and deny entries. A broad graph label is a prompt to inspect the actual permission, not a substitute for it.

| Observation | Follow-up |
| --- | --- |
| User is in Helpdesk | Determine what that group is authorized to do and on which object |
| Recursive list contains the user | Recover the direct links that explain the nesting |
| Group appears in directory but not the session | Check collection/logon time and token context |
| Local administrator membership on host A | Do not infer the same on host B or access through every protocol |
| Access denied after a valid login | Check resource authorization before retrying the password |

Stop this branch when you can record identity → group chain → permission → target → observed result, or name the missing prerequisite. Continue through the [AD credentials journey](/active-directory/methodology) for a complete example.

## Follow identity, membership and resource permission

A username becomes useful when you know what its groups and object rights allow it to access. Record stable identifiers and distinguished names, then trace the relationship to a specific host, share, service or directory object. Group names are hints; effective permissions are evidence.

### Query the identity and its groups

```powershell
Get-ADUser USERNAME -Properties MemberOf,Description,ServicePrincipalName,PasswordLastSet
Get-ADPrincipalGroupMembership USERNAME | Select-Object Name,GroupScope,GroupCategory
Get-ADGroup GROUP_NAME -Properties Members,MemberOf,Description
Get-ADGroupMember GROUP_NAME -Recursive
```

Recursive membership answers a different question from a group's direct members. Retain direct relationships when explaining a path. Compare directory state with the running process token:

```powershell
whoami /user
whoami /groups
```

A newly added membership may need a fresh authentication context. Built-in local groups on a workstation/server are also distinct from domain groups with similar names.

### Inspect service accounts as accounts with a purpose

```powershell
Get-ADUser -Filter {ServicePrincipalName -like '*'} -Properties ServicePrincipalName,Description,MemberOf,PasswordLastSet
Get-ADServiceAccount -Filter * -Properties PrincipalsAllowedToRetrieveManagedPassword,ServicePrincipalNames
```

A service account may be a normal user, a computer account or a managed account. Its SPNs, retrieval permissions, group memberships and object ACLs determine which next checks make sense. Do not treat readable gMSA metadata as permission to retrieve its managed password.

### Connect policy to actual scope

```powershell
Get-GPO -All | Select-Object DisplayName,Id,GpoStatus
Get-GPInheritance -Target 'OU=Workstations,DC=example,DC=local'
Get-GPOReport -Name 'POLICY_NAME' -ReportType Html -Path .\policy-report.html
```

The GroupPolicy module is required. Substitute the real OU distinguished name. Check links, enforced/block-inheritance behavior, security filtering, WMI filtering and the setting itself. Read access to a GPO is not permission to modify it, and modification is not proof that a selected host applies it.

### Validate the destination

For a membership that grants access to a file share, verify the share. For a host-admin relationship, inspect the host's relevant local group and test the intended management protocol. For an ACL edge, resolve the exact right and object type before selecting a change.

```bash
nxc smb TARGET_IP -d DOMAIN_FQDN -u USERNAME -p 'PASSWORD' --shares
smbclient //TARGET_FQDN/KNOWN_SHARE -U 'DOMAIN_FQDN/USERNAME'
```

Preserve the identity, membership chain, target permission and observed result together. If a graph path fails, test each edge in order; stale collection data or an absent network path can explain the failure without invalidating every relationship.

## Windows — inspect the current session

```cmd
whoami /groups
whoami /priv
net user USER /domain
```

With the ActiveDirectory PowerShell module:

```powershell
Get-ADPrincipalGroupMembership -Identity USER | Select-Object Name,GroupScope
Get-ADGroupMember -Identity 'GROUP_NAME' -Recursive
```

## What the result means

| Membership | Next check |
| --- | --- |
| Remote Management Users | WinRM enabled, endpoint permissions, and network reachability; membership is not local admin. |
| Remote Desktop Users | RDP service and logon policy; a deny-logon policy can still block access. |
| Backup Operators | Effective SeBackupPrivilege/SeRestorePrivilege and the tool's backup semantics; locked files may need a consistent snapshot. |
| Group Policy Creator Owners | Creating a GPO and linking it to an OU are separate permissions. |
| Protected Users | Check authentication restrictions before expecting NTLM or reusable cached credentials. |

## Membership changed but access still fails

The directory object, your existing Windows access token, and cached tickets can reflect different moments. Use a fresh authenticated session when testing changed membership. Refreshing Kerberos tickets alone does not replace an existing process's access token.
