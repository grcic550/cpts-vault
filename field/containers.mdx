## Determine whether the shell is inside a container

Container identity and host identity can differ. First inspect the environment, mounts, process tree and runtime access. Root inside a constrained container is not automatically root on the host; a host-mounted filesystem or runtime socket can change the boundary substantially.

```bash
id
hostname
cat /proc/1/cgroup
cat /proc/self/mountinfo
ls -la /.dockerenv /run/.containerenv 2>/dev/null
ls -la /var/run/docker.sock /run/containerd/containerd.sock 2>/dev/null
```

These are indicators, not universal container detectors. Cgroup versions and runtime configurations vary. Check paths and permissions rather than assuming a missing marker proves a bare-metal host.

### Inspect mounts and runtime visibility

```bash
mount
findmnt
# Only where the current identity legitimately reaches the Docker daemon:
docker context ls
docker ps --no-trunc
docker inspect CONTAINER_ID
```

Read bind mounts, privileged settings, capabilities, user mappings and network mode. Docker client installation is different from daemon access. A runtime socket can grant powerful control over its host; establish which daemon/host you are talking to before interpreting any command.

### Trace a concrete boundary

A readable application secret may authenticate to another service. A writable host mount may affect a host process. A permitted runtime operation may create a different execution context. Each is a separate path with its own rights and evidence. Inspect the actual source/destination mount and the process that consumes it.

```bash
ls -ld /MOUNT_POINT
ls -la /MOUNT_POINT
cat /proc/self/status
```

Do not equate any one capability or a writable directory with an escape. For an authorized escape exercise, verify the required runtime setting, host resource and triggering operation before applying the retained example. Record the resulting host/identity afterward so container-local and host-level access remain distinguishable.

## Linux shell — inspect context

```bash
id
cat /proc/1/cgroup
ls -l /.dockerenv /var/run/docker.sock
cat /proc/self/status | grep -E 'Cap|Seccomp'
```

These are clues. A missing .dockerenv file or an uninformative cgroup path does not rule out a container.

## If a Docker daemon is accessible

```bash
docker context show
docker ps
docker inspect CONTAINER_NAME
```

Check the selected daemon/context, mounts, namespaces, capabilities, and socket ownership. The ability to control a privileged host daemon can be more significant than your UID inside the current container.

## Avoid false conclusions

- Seccomp disabled is not by itself proof of privileged-container mode.
- A visible socket is not necessarily readable or usable by your account.
- Host-looking paths may still be container mounts; confirm what filesystem and daemon you are inspecting.
- Access to a container subnet may require a route or forward from the pivot.
