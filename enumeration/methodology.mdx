## Start with a target, finish with a service hypothesis

Use this journey when you have a target IP and need to decide where to begin. The worked example uses `10.129.10.10`; replace it with your assigned lab address. Commands run on Kali with a working lab route. Keep the target, time, source network position and identity beside each observation. A result from outside a pivot does not describe reachability from inside it.

The useful output is a small evidence map: **port → confirmed service → authentication state → accessible resource → next hypothesis**. You do not need to finish every service before following a strong lead, but record untested services so they are not forgotten.

### 1. Establish your route and record the scan

```bash
TARGET_IP='10.129.10.10'
mkdir -p evidence/nmap evidence/smb
ip route get "$TARGET_IP"
nmap --version
```

The route should use your intended lab interface or tunnel. If it points at an unrelated local subnet, fix that before interpreting timeouts. Ping is optional evidence: a failed ICMP reply alone does not establish that a target is down.

**Discover TCP ports**

Run in: **Kali, direct or routed lab access**. Requires: Target IP and working route.

```bash
nmap -sT -p- -T3 --open -oA evidence/nmap/tcp-all "$TARGET_IP"
```

**What this establishes:** A saved port inventory from this network position. Open means a listener answered; filtered does not establish absence.

**If Host appears down:** Validate route and discovery behavior before choosing a justified -Pn retry.

**Next:** Use discovered ports in the service-identification pass.

Use the full TCP discovery output to select the next ports, rather than automatically enumerating only familiar defaults. If the target is known to be live but discovery prevents scanning, repeat an appropriate targeted check with `-Pn` and document why. `-Pn` skips discovery; it does not repair routing or bypass a firewall.

**Identify the discovered services**

Run in: **Kali**. Requires: Replace the port list with observed open ports; review default-script behavior.

```bash
nmap -sT -sV -sC -p 22,80,445 -oA evidence/nmap/services "$TARGET_IP"
```

**What this establishes:** Version probes and default script output help identify the service behind the port.

**If No useful banner:** Use a protocol-specific client and compare negotiation; do not infer software solely from the port number.

**Next:** Choose the service branch supported by the response.

Compare the banner, protocol negotiation and service-specific behavior. A high-numbered port can run SMB or HTTP; a standard port number is only a starting clue. If you need UDP coverage, add a separate privileged pass and retain uncertain states:

```bash
sudo nmap -sU --top-ports 20 -sV -oA evidence/nmap/udp-top "$TARGET_IP"
```

`open|filtered` does not confirm a listening application. Follow an ambiguous UDP result with a protocol-appropriate request. A large silent scan is not better evidence than a smaller interpretable one.

### 2. Choose the branch from the actual service

| Observation | Next useful check | Preserve |
| --- | --- | --- |
| HTTP redirect or certificate names | Resolve the name and map that application | URL, hostname, redirect and session |
| SMB negotiation succeeds | Compare unauthenticated and supplied-identity access | Server/domain name and exact identity |
| DNS is exposed | Query the relevant zone and record authoritative answers | Resolver, zone and returned names |
| Database listener | Determine the required authentication mode | Instance, port, login result and privileges |
| FTP/NFS/SNMP | Inspect allowed service access before choosing an exploit | Authentication or export/community context |

The rest of this journey follows an observed SMB listener. For other services, use the corresponding sections in the preserved reference below or the [service directory](/tools/index).

### 3. Establish SMB authentication separately from share access

```bash
smbclient --version
smbclient -L "//$TARGET_IP" -N
```

This attempts the explicitly passwordless context. A refused anonymous listing does not eliminate authenticated SMB access. Keep `NT_STATUS_LOGON_FAILURE`, `NT_STATUS_ACCESS_DENIED` and a connection timeout distinct. Do not infer that a supplied password is wrong from a failure that happened before authentication.

**List shares with a known identity**

Run in: **Kali**. Requires: An observed SMB endpoint and a supplied LAB/student identity.

```bash
smbclient -L "//$TARGET_IP" -U 'LAB/student'
```

**What this establishes:** Password prompt followed by a share list or a specific authentication/authorization error.

**If NT_STATUS_LOGON_FAILURE:** Check domain versus local account context and the supplied credentials without repeated guessing.

**Next:** Select an actually advertised share and test access separately.

If NetExec is already installed, its service summary is another view of the same hypothesis, not a reason to launch unrelated protocols:

```bash
nxc --version
nxc smb "$TARGET_IP" -d lab.htb -u student -p 'LAB_PASSWORD' --shares
```

The password here is a placeholder and command-line arguments may be visible in process listings/history. Prefer the prompted smbclient operation above when it answers your question. Use a domain identity only when it is actually a domain account; a local account requires the relevant local authentication context. Avoid repeated authentication attempts while the identity or policy is uncertain.

### 4. Test one discovered resource

**Connect to one discovered share**

Run in: **Kali**. Requires: Replace READABLE_SHARE with a real share; same identity as the listing.

```bash
smbclient "//$TARGET_IP/READABLE_SHARE" -U 'LAB/student'
```

**What this establishes:** An smb prompt establishes a connected share session; reading each file remains a separate check.

**If NT_STATUS_ACCESS_DENIED:** Retain the successful login evidence and inspect the target share permission.

**Next:** List files and retrieve one relevant readable file; record what it contains and its source.

Within the SMB prompt, inspect first, then retrieve a specific relevant file:

```text
pwd
ls
cd department
ls
get application.conf evidence/smb/application.conf
exit
```

Replace the directory and filename with observed values. The local `evidence/smb` directory must exist. A listing establishes the ability to enumerate names; a successful `get` establishes reading that file. Neither establishes write permission, administration or command execution.

| Result | Interpretation | Next action |
| --- | --- | --- |
| Login succeeds, share connection denied | Identity accepted; that resource is not authorized | Verify the exact share and identity; examine other advertised resources |
| Share connects, a file is denied | Directory/file permissions differ | Record which objects are readable; avoid treating all share contents as equivalent |
| Configuration contains a host or account | A new scoped lead, not a verified login | Identify the application/service and validate only that relevant access path |
| Timeout during reads | Transport/session problem remains possible | Compare a small listing, connection logs and route before changing credentials |

### 5. Write the next hypothesis and a coverage checkpoint

A useful note says: “As LAB/student from Kali, I listed the Finance share and read application.conf. It names an internal database. Next I will check whether that database is reachable from my current position.” This separates a fact from the proposed test.

Before moving on, record discovered services, which identities you tried, resources tested, exact blockers and promising untested leads. Revisit when you gain credentials, a new hostname, a different network position or a more privileged session. Enumeration is sufficiently covered for the current hypothesis when you can explain those states; it is not proof that the host has no remaining weaknesses.

Continue with [web mapping](/web/methodology), [domain identity and permissions](/active-directory/methodology), or [internal reachability](/pivoting/methodology), according to the evidence. Tool details remain in [Nmap](/commands/nmap), [NetExec](/commands/netexec) and [smbclient](/commands/smbclient).

## Command walkthrough: from an IP to useful leads

Run these from the intended lab network position. Replace the example IP/domain and record which session or pivot produced the result. Choose the service commands that match discovered ports; the goal is an inventory, not running every tool against every host.

### Discover ports, then identify services

```bash
TARGET_IP='10.129.10.10'
mkdir -p evidence/nmap
nmap -sT -p- -T3 --open -oA evidence/nmap/tcp-all "$TARGET_IP"
nmap -sT -sV -sC -p 22,80,445 -oA evidence/nmap/services "$TARGET_IP"
```

Replace `22,80,445` with the actual open ports. `-sV` probes service versions; `-sC` runs the default script set, so review whether that behavior fits the lab scope. `--open` filters the displayed results; it does not make every omitted port conclusively closed. If discovery is blocked but the host is known to be reachable, investigate the reason before deciding whether `-Pn` fits the situation.

```bash
# A separate UDP pass when required; this needs suitable privileges.
sudo nmap -sU --top-ports 20 -sV -oA evidence/nmap/udp-top "$TARGET_IP"
```

UDP silence can mean filtering or a service that does not respond to that probe. Record `open|filtered` honestly rather than converting it to a confirmed open service.

### DNS and hostnames

```bash
dig @"$TARGET_IP" lab.htb A
dig @"$TARGET_IP" lab.htb MX
dig @"$TARGET_IP" lab.htb NS
dig @"$TARGET_IP" lab.htb TXT
dig @"$TARGET_IP" lab.htb AXFR
```

Use these when the target actually provides DNS for the relevant lab zone. An AXFR refusal is a normal result, not a reason to abandon other records. Feed confirmed names into web and domain enumeration.

### SMB and RPC

```bash
# Test the explicitly unauthenticated session separately.
smbclient -L "//$TARGET_IP" -N
rpcclient -U '' -N "$TARGET_IP" -c 'srvinfo; enumdomusers'

# Then use a valid lab identity; these forms prompt for its password.
smbclient -L "//$TARGET_IP" -U 'LAB/student'
smbclient "//$TARGET_IP/READABLE_SHARE" -U 'LAB/student'
rpcclient -U 'LAB/student' "$TARGET_IP" -c 'enumdomusers; enumdomgroups'
```

Inside a share, inspect before copying:

```text
ls
cd department
ls
get application.conf
```

Share listing, connecting, reading, and writing are separate permissions. Use a discovered share name. A successful login with an empty listing may still be a restricted identity.

### FTP and NFS

```bash
ftp "$TARGET_IP"
showmount -e "$TARGET_IP"
```

For FTP, record whether the lab permits anonymous access or supplies credentials, then inspect `pwd` and `ls`. For an exposed NFS export, use its real export path and a read-only mount for inspection:

```bash
sudo mkdir -p /mnt/lab-nfs
sudo mount -t nfs -o ro "$TARGET_IP:/EXPORTED_PATH" /mnt/lab-nfs
ls -la /mnt/lab-nfs
```

An export being advertised does not prove your client can mount it. Client restrictions and UID/GID mapping affect access.

### SNMP and databases

```bash
# Use a community string known or explicitly being tested in the lab.
snmpwalk -v2c -c LAB_COMMUNITY "$TARGET_IP" 1.3.6.1.2.1.1

# Interactive database access with a supplied identity.
mysql -h "$TARGET_IP" -P 3306 -u student -p
impacket-mssqlclient 'LAB/student@10.129.10.10' -windows-auth
```

For SQL authentication, choose the MSSQL client's SQL-auth form instead of `-windows-auth`. A TCP connection, a successful database login, and privileged query access are different milestones.

## Use the result to decide the next action

| Finding | Immediate next step |
| --- | --- |
| A second hostname or redirect | Confirm a distinct application and enumerate its features |
| Readable configuration or backup | Identify its application/service, credential scope, and internal names |
| Domain users or a valid domain identity | Follow the AD identity and permission workflow |
| An authenticated database session | Inspect selected database, accessible schemas, and account privileges |
| Internal addresses in files/routes | Record the origin of the lead and check reachability from the relevant pivot |

Save raw output and a short interpretation. The important handoff is “this evidence makes this check appropriate,” not a list of commands that happened to run.

## First pass: build the service map

1. Record the target, supplied names, network connection, and whether you are testing directly or through a pivot.
2. Use the [existing scan reference](/commands/nmap) to discover reachable ports, then identify the services on those ports. Keep the output. Do not treat a conventional port number as proof of the service.
3. Record hostnames, domains, redirects, banners, and certificate names. Confirm which names actually resolve to your lab target.
4. Make one row per service: port, protocol, confirmed product, hostname, authentication available, access tested, useful evidence, next check.
5. Visit every discovered service before spending the whole session on one exploit idea. Keep UDP and filtered or unreachable services marked as untested where appropriate.

## How to recognize a useful lead

A useful lead changes what you know or can access: a readable backup, a configuration file, a valid service account, a second hostname, an internal address, a writable resource, or a confirmed software feature. Record where it came from and what it may enable. A version string alone is a research lead; check the exact product, configuration, affected behavior, and prerequisites before treating it as a vulnerability.

If you discover credentials in the lab, record their likely scope: local account, domain account, database login, or application account. Test the specific relevant service and record the outcome. One accepted login does not establish permissions everywhere.

## Troubleshoot before changing technique

- **No response:** compare direct access and the intended pivot route; check address, port, name, and protocol.
- **Authentication fails:** verify identity format, authentication mechanism, and whether this is the expected host or realm.
- **Authentication succeeds, access denied:** enumerate the actual account permissions and resource ACLs.
- **Empty output:** distinguish no data from a restricted session or unsupported operation.
- **Nothing promising:** revisit untested services and relationships between services. A file obtained through one service can explain another application.

## Move on when

You can account for each discovered service, have saved the evidence, and can name either a justified next check or the reason a branch is currently blocked. Revisit the map whenever you obtain a new account or reach another subnet.
