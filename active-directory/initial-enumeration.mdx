Map hosts, services, and users from the first internal vantage point.

[AD study path](/active-directory/index) · [Command reference](/active-directory/command-reference) · [Troubleshooting](/active-directory/troubleshooting)

> **Correction:** Kerbrute user enumeration can generate event 4768 when Kerberos auditing is enabled. It is not invisible. [Kerbrute documentation](https://github.com/ropnop/kerbrute).

For our initial enumeration on this module, we are it seems doing internal enumeration. This can be done a lot of ways but for us to actually enumerate internally (as agreed in the scope of the testing that our client specified) we need to have access to inside of the network.

This can be done multiple ways:

1. A penetration testing distro (typically Linux) as a virtual machine in their infrastructure that calls back to a jump host we control over the VPN, and we can SSH into.
2. A physical device plugged into an ethernet port that calls back to us over VPN
3. A physical presence in their office with our laptop plugged into their ethernet port
4. A Linux VM in either Azure or AWS with access to the internal network what we can SSH into using public key authentication and our publiv IP address whitelisted.
5. VPN accesss into their internal network
6. From a corporate laptop connected to the clients VPN
7. On a managed workstation physically sitting in their office with limited or no internet access or ability to pull in tools. They might also  allow internet usage and to pull in tools.
8. On a VDI (virtual desktop) accessed using Citrix or the like, with one of the configurations described for the manged workstation typically accesible over VPN either remotely or from a corporate laptop.

## Key Data Points!!!

1. AD Users - We are trying to enumerate valid user accounts we can target for password spraying
2.  AD Joined Computers - Key computers that we target include Domain Controllers, file servers, SQL servers, Mail Exchange servers, database servers, etc.
3. Key services - Kerberos, NetBIOS, LDAP, DNS,...
4. Vulnerable Hosts and Services - Anything that can be a quick win (a.k.a an easy host to exploit and gain a foothold)

Enumerating AD is hard without planning. Methodology important!!! 

No matter how we proceed we typically start at the same place and look for the same data points. 

Passive indentification and active validation of the results. Afterwards we probe. Afterwards we stop, group and anaylize what we got. Hopefully credentials or user account.

## Tools and techniques

We can use Wireshark or TCPDump to inspect network and intercept packets and analyse them. this is especially helpful in black box approach.

It is usefull to save what we scan with wireshark and tcpdump (PCAP traffic). if we cannot transfer tools for example to windows, we already have installed network monitoring tool known as pktmon.exe which is installed to all editions of windows 10.

It should be noted that I connected to their linux VM with xfreerdp and there used wireshark and other tools.

We use **Responder** to analyse network traffic.

It is a tool built to listen, analyze, and poison LLMNR, NBT-NS, and MDNS requests and responses.

Here we can find some hosts that we did not find with wireshark and it is worth it to note them down.

active checks we can perform with **fping**.

it provides similar capability as the standard ping application in that it utilizes ICMP requests and replies to reach out and interact with the host. it shines in its ability to send requests to mulitple hosts at once. it runs in cyclical manner instead of waiting. this is not one-stop-shop but it will tell as an inital idea of what exists.

fping flags:
1. a - to show targets that are alive
2. s - to print stats at the end of the scan
3. g - to generate a target list from the CIDR network
4. q - to not show per-target results

example:

```bash
fping -asqg 172.16.5.0/23
```

Next we can proceed to **nmap scanning** for more detailed scan of the alive targets for active services and their ports. We want to identify critical hosts such as Domain Controllers and web servers, and identify potentially vulnerable hosts to probe later.

In AD it would be nice to focus on accompanying AD services such as ***DNS,SMB,LDAP, and Kerberos***

example of the scan:

```bash
sudo nmap -sS -v -A 172.16.5.5 172.16.5.130 -oN /home/htb-student/Documents/hosts-enum
```

this uses stealth, v prints steps, -A stands for aggresive and -oN outputs normal text to read by human.

it is good practice here to look for older software that some large enterprise environments still use so we can exploit them easily.

we need to be aware how our tools work. nmap could cause instability in the system or take it offline which can cause issues. we need to understand the scans we take. 

## Identifying Users

So, if our client does not give us a user to start testing with (which is often the case), we will need to find a way to establish a foothold in the domain by either obtaining credentials or NTLM password hash for a user, a SYSTEM shell on a domain-joined host, or shell in the context of a domain user-account.

The access, even the lower one, offers a lot of opportunities.

***Kerbrute - Internal AD Username Enumeration***

As the title says, kerbrute is a tool for username enumeration among other things. It is considered a stealthier option for domain account enumeration because it uses Kerberos responses to distinguish accounts; event 4768 can still be generated when Kerberos auditing is enabled. We use Kerbrute in conjuction with wordlists that contain usernames. In this section I used jsmith.txt or jsmith2.txt from [Insidetrust](https://github.com/insidetrust/statistically-likely-usernames). 

We then point Kerbrute at Domain Controller we found earlier and feed it a wordlist.

## Identifying potential vulnerabilities

the local system account **NT AUTHORITY\SYSTEM** is a built-in account in Windows  operating systems. It has the highest level of access in the OS  and is used to run most Windows services.

A `SYSTEM` account on a `domain-joined` host will be able to enumerate Active Directory by impersonating the computer account, which is essentially just another kind of user account. Having SYSTEM-level access within a domain environment is nearly equivalent to having a domain user account.

there are multiple ways to gain system level access on a host:
1. remote windows exploits such as eternalblue
2. abusing service that is running in the context of SYSTEM account, or abusing the service account SeImpersonate privileges using JuicyPotato.
3. Local privilege escalation flaws in Windows operating systems such as the Windows 10 Task Scheaduler 0-day
4. Gaining admin access on a domain-joined host with a local account and using Psexec to launch a SYSTEM cmd window

By gaining SYSTEM-level access on a domain-joined host, you will be able to perform actions such as, but not limited to:

- Enumerate the domain using built-in tools or offensive tools such as BloodHound and PowerView.
- Perform Kerberoasting / ASREPRoasting attacks within the same domain.
- Run tools such as Inveigh to gather Net-NTLMv2 hashes or perform SMB relay attacks.
- Perform token impersonation to hijack a privileged domain user account.
- Carry out ACL attacks.

we need to be cautious when performing these active tasks against AD environment to not get caught. If we are performing evasive scanning then it is okay but if not then we have to be stealthy and mimic real world attackers.
