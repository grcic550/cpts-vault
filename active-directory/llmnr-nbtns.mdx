## LLMNR/NBT-NS Poisoning - from Linux


We will work through two different techniques side by side: network poisoning and password spraying. We want to acquire cleartext credentials for domain account thereby gaining us a foothold in the domain.

We will perform man-in-the-middle attack on Linked-Local Multicast Name Resolution (LLMNR) and NetBIOS Name Service (NBT-NS) broadcasts. Depending on the network, we may get low-privileged or administrative level password hashes that can also sometimes be used to perform SMB relay attacks.

***LLMNR & NBT-NS Primer***

They are used if DNS fails for host identification. If DNS fails for some reason then LLMNR is used and it asks all machines on the local network for the correct host address. LLMNR is based upon the Domain Name System (DNS) and allows the hosts on the same local link to perform name resolution for other hosts. It uses port 5355 over UDP. If LLMNR fails then NBT-NS will be used. It identifies systems on a local network by their NetBIOS name. It utilizes port 137 over UDP.

The thing is, when LLMNR and NBT-NS are used for name resolution, ANY host on the  network can reply. This is where we come in with the Responder and poison these requests. We can poison the authoritative name resolution source in the broadcast domain by responding to LLMNR nad NBT-NS traffic as if they have the answer for the requesting host. This poisoning effort is done to get the victims to communicate with our system by pretending we know about the requested host. If the requested host requires authentication then we capture NetNTLM hash and attempt offline password recovery or relay a live authentication exchange where the protocol permits; the captured NetNTLM response is not an NT hash for pass-the-hash. We can then use it against different protocols such as LDAP.

Example for LLMNR/NBT-NS poisoning.

1. Let's say the host is attempting to connect to \\print1.inlanefreight.local but accidentally types in \\printer1@inlanefreight.local 
2. DNS server responds with not knowing this host
3. Then host broadcasts request to the entire network asking if anyone knows this host and its location (\\printer1@inlanefreight.local)
4. We (the attacker with Responder) respond to the host stating that we are the \\printer1@inlanefreight.local
5. The host believes us and sends a username and a NetNTLMv2 challenge-response to authenticate
6. We then attempt to crack the captured NetNTLMv2 response offline and use it elsewhere.

how to check if target is vulnerable to LLMNR and NBT-NS:
Based on the module content, here are a few ways to check for this vulnerability:

### 1. Active Poisoning (The Attacker's Method)

The most direct way to test for vulnerability is to attempt the attack itself in a controlled manner. As demonstrated in this section and the previous one, you can use a tool to listen for LLMNR and NBT-NS queries.

- **On Windows:** Use a tool like **Inveigh**, as covered in the "LLMNR/NBT-NS Poisoning - from Windows" section. If you run `Inveigh.exe` or `Invoke-Inveigh` and immediately start seeing name resolution requests and capturing hashes, the network is vulnerable.
- **On Linux:** Use a tool like **Responder**. If you run it and it captures authentication hashes, you've confirmed the vulnerability.

If these tools successfully capture hashes, it proves that:

- Hosts on the network are using LLMNR/NBT-NS for name resolution.
- These protocols are not disabled.
- You can successfully poison responses and trick clients into authenticating to you.

### 2. Passive Network Monitoring

You can passively listen to network traffic to see if the protocols are in use.

- Use a network analyzer like **Wireshark** or **tcpdump**.
- Filter for traffic on the ports used by these protocols:
    - **LLMNR:** `UDP port 5355`
    - **NBT-NS:** `UDP port 137`

If you see broadcast or multicast traffic on these ports from various hosts, it means the protocols are active on the network and likely vulnerable to poisoning.

### 3. Host-Level Configuration Check

You can check the configuration of an individual Windows host to see if it has these protocols enabled. The "Remediation" part of this section gives us the clues.

- **To check for LLMNR:**
    
    - Open the Local Group Policy Editor (`gpedit.msc`).
    - Navigate to `Computer Configuration -> Administrative Templates -> Network -> DNS Client`.
    - Check the status of "**Turn off multicast name resolution**". If it is "Not Configured" or "Disabled", then LLMNR is enabled and the host is vulnerable.
- **To check for NBT-NS:**
    
    - Open your network adapter's properties.
    - Go to `Internet Protocol Version 4 (TCP/IPv4) -> Properties -> Advanced -> WINS` tab.
    - Look at the "NetBIOS setting". If "**Disable NetBIOS over TCP/IP**" is not selected, then NBT-NS is enabled.

In summary, the easiest and most definitive way for a penetration tester to check for vulnerability is to run a tool like **Inveigh** or **Responder**. If you capture hashes, the network is vulnerable.
