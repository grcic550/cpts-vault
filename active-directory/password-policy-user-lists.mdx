## Password Spraying

Password spraying is an important method and technique of accesing systems and services by targeting multiple accounts with common passwords. This way the risk of locking out accounts is lower. Even the lowest privileged user withing the Domain can be useful in moving further through the domain. 

For password spraying we would first need good username list. We can get one from github for most common usernames. for example jsmith.txt one. We can also use some scrapers an pull names from linkedin or use OSINT to find out more about our target through contact pages or pdf files. Another important thing is password policy. It can significantly increase our chances of succesfully performing password spraying since we have narrower choice of usernames and more knowledge about lockout.

There is usually a timeout between attempting passwords so we have to take that into consideration.

### Enumerating and retrieving password policies

### Summary: Enumerating & Retrieving Password Policies

This section details various methods for discovering an Active Directory domain's password policy, which is a critical step for planning attacks like password spraying. The techniques are divided based on whether you have credentials and the operating system you are attacking from.

#### Key Enumeration Methods

1. **Credentialed Enumeration (from Linux):**  
    If you have valid domain credentials, you can directly query the password policy. The section demonstrates using `CrackMapExec` (NetExec now) with the `--pass-pol` flag to retrieve detailed policy information, including minimum password length, password history, lockout threshold, and complexity requirements.
    
2. **Uncredentialed Enumeration (from Linux):**  
    Without credentials, enumeration relies on finding common misconfigurations:
    
    - **SMB NULL Sessions:** This legacy misconfiguration allows an unauthenticated user to connect to the IPC$ share and query domain information. Tools like `rpcclient`, `enum4linux`, and its modern successor `enum4linux-ng` can exploit this to dump the password policy.
    - **LDAP Anonymous Binds:** Another legacy setting where unauthenticated users can perform LDAP queries. The `ldapsearch` tool can be used to query domain objects and filter for password policy attributes like `pwdHistoryLength` and `minPwdLength`.
3. **Enumeration from Windows:**
    
    - **With Credentials:** On a domain-joined machine, the built-in `net accounts /domain` command provides a clean, readable summary of the password policy. For more detailed, object-oriented output, PowerShell tools like PowerView (`Get-DomainPolicy`) are extremely effective.
    - **Without Credentials:** You can test for a NULL session from Windows using the `net use \\<HOST>\ipc$ "" /u:""` command. The section also shows common error codes you might receive when authentication fails, which can help diagnose if an account is disabled, locked out, or if the password is simply incorrect.

#### Analyzing the Policy for Attacks

Once the policy is retrieved, you must analyze it from an attacker's perspective. The section uses the `INLANEFREIGHT.LOCAL` domain as an example to highlight key attributes:

- **Minimum Password Length (8):** A low minimum length increases the chances of weak, guessable passwords.
- **Account Lockout Threshold (5):** This tells you how many bad password attempts you can make before an account is locked. A threshold of 5 does not guarantee any safe number of guesses: existing failures, concurrent authentication, and the effective policy also matter.
- **Lockout Duration (30 minutes):** This indicates how long a locked account will remain inaccessible. Knowing this helps time subsequent spray attempts to avoid causing a denial-of-service condition.
- **Password Complexity (Enabled):** While it sounds secure, this often just means users add a capital letter, a number, and a special character to a common word (e.g., `Summer2024!`), which is still highly susceptible to password spraying.

The primary takeaway is that a "weak" policy (low length, high lockout threshold) makes password spraying a highly effective and relatively low-risk attack vector. The section concludes with a critical warning: **never lock out user accounts**. If the effective policy is unknown, establish it and the agreed testing limits before selecting a spray schedule.



## Password Spraying - Making a target user list

To be able to perform a spraying attack we need to be able to perform it on some account or computer. THat is why we first need a list of user names. Valid ones. We can  get this list of users in a couple of ways depending if we have access to active directory aka we are inside or if we do not have credentials or null SMB session. There we can use tools like kerbrute or crackmapexec to search for valid usernames with predefined lists or we can make our own.

If we are talking about already posessing credentials or there is a SMB NULL session that doesn't require password then it is much easier. We can also use LDAP anonymous bind to query LDAP anonymously. We can use credentials we obtained somewhere else somehow. 

With having these credentails or null session of smb, we can enumerate password policy which can help us a lot in narrowing down user names and helping us making our own list with set of rules. Password policy can also contain rules for account lockout so  we have to be vary of that.

For SMB NULL sessions some tools that we can use are num4linux, rpcclient, crackmapexec.

for example this command:

```bash
enum4linux -U 172.16.5.5 | grep "user:" | cut -f2 -d"[" | cut -f1 -d"]"
```

this command would give us list of user names. cut command is just to remove user prefix and something afterwards of actual usernames.

we can also use rpcclient:

```bash
rpcclient -U "" -N 172.16.5.5
```

-U stands for null session so no user and -N is for no password.
there we can use **enumdomusers** to get userlist


## using ldap search

```bash
grcic550@htb[/htb]$ ldapsearch -h 172.16.5.5 -x -b "DC=INLANEFREIGHT,DC=LOCAL" -s sub "(&(objectclass=user))"  | grep sAMAccountName: | cut -f2 -d" "
```

If we do not have credentials then we can use Kerbrute, It works in a way that it sends an AS-REQ to a KDC  without Kerberos Pre-Authentication and if KDC returns PRINCIPAL UNKNOWN than there is no such user, but if it returns asking for Kerberos Pre-Authentication that means that user was accepted and that user exists. These requests can generate event 4768 when Kerberos auditing is enabled. When performing password spraying that is another case.

```bash
kerbrute userenum -d inlanefreight.local --dc 172.16.5.5 jsmith.txt
```
