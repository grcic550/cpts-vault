## 2 Check DNS and time

Confirm that the domain controller is reachable and its name resolves before debugging AD tools.

### Before you start

- The domain name, DC IP, and DC hostname supplied by the lab or discovered during enumeration.
- dig installed on Linux; do not guess a DC hostname.

### Check the route to the DC

```bash
ip route get {{dcIp}}
```

### Ask the DC for domain records

```bash
dig @{{dcIp}} _ldap._tcp.dc._msdcs.{{domain}} SRV
dig @{{dcIp}} {{dcHost}} A
```

### Compare UTC time with the lab DC

```bash
date -u
```

### What a useful result looks like

The route uses your lab connection. DNS returns the lab DC records. Compare your UTC time with the DC time reported by the lab or a service; date alone does not prove clock synchronization.

### If something goes wrong

- A DNS timeout can mean a wrong route, blocked DNS, or an incorrect DC address.
- Direct dig queries do not configure your system resolver. Follow the troubleshooting note if tools still cannot resolve names.
- Kerberos clock-skew errors require checking both clocks; do not blindly change your system time.

### Confirm and record

- [ ] Confirm the DC IP and hostname against DNS or lab evidence.
- [ ] Resolve routing, DNS, and clock issues before using Kerberos.

## 3 Find exposed services

Build a service inventory and choose the next relevant note.

### Before you start

- A reachable target from your assigned lab.
- Nmap installed. The output directory from workflow 1.

### Start with a small TCP service inventory

```bash
mkdir -p scans
nmap -sT -sV --top-ports 100 {{target}} -oA scans/initial
```

### What a useful result looks like

A saved report identifies open ports and service hints. This is a starting sample, not a full TCP or UDP assessment.

### If something goes wrong

- If the host is reported down, verify the VPN and address first. The full Nmap note explains when -Pn is appropriate.
- Filtered ports do not prove that a service is absent.
- Do not treat a detected service version as proof of a vulnerability.

### Confirm and record

- [ ] Record open ports and service names.
- [ ] Plan the wider TCP/UDP coverage using the Nmap reference.

## 4 Enumerate with domain credentials

Verify a known account and inspect the share list before choosing a deeper path.

### Before you start

- A valid lab account and target offering SMB.
- smbclient on Linux. Enter the password at its prompt; it is not saved in this guide.

### List shares with a known account

```bash
smbclient -L {{target}} -U {{identity}}
```

### What a useful result looks like

A successful response lists shares visible to the account. Listing a share does not prove you can read every file inside it.

### If something goes wrong

- LOGON_FAILURE: check the account format and credential once. Repeated retries can lock accounts.
- ACCESS_DENIED may describe share permissions rather than a bad password.
- Use the SMB reference for opening a specific share and recording interesting file paths.

### Confirm and record

- [ ] Record which identity authenticated and where.

## 5 Understand your Windows shell

Identify the current account, memberships, and network context.

### Before you start

- An existing Windows shell in the lab.
- Use the PowerShell tab for the environment example.

### Identify token groups and privileges

```powershell
whoami /all
```

### Inspect network configuration

```powershell
ipconfig /all
```

### Record user and computer context

```powershell
$env:COMPUTERNAME
$env:USERDOMAIN
$env:USERNAME
$env:LOGONSERVER
```

### What a useful result looks like

The output identifies the current token and network. Environment variables are context hints; verify domain relationships with the full enumeration notes.

### If something goes wrong

- A local account is different from a domain account with the same username.
- A remote shell does not automatically delegate credentials to a second host; see the double-hop note.

### Confirm and record

- [ ] Record the computer, identity, and relevant groups.
- [ ] Record whether the shell is local, remote, and elevated.

## 6 Start BloodHound and import data

Open your Kali BloodHound setup and collect data in the CE format.

### Before you start

- Kali BloodHound and bloodhound-ce-python installed.
- Valid domain credentials, working DNS, and a reachable DC.

### Start your Kali BloodHound setup

```bash
sudo bloodhound-start
```

### Collect domain data for BloodHound CE

```bash
bloodhound-ce-python -u {{username}} -d {{domain}} -ns {{dcIp}} -dc {{dcHost}} -c DCOnly --zip
```

### What a useful result looks like

Use the URL printed by the launcher (normally http://127.0.0.1:8080/ui/login on Kali). Your existing setup uses Neo4j; the launcher handles its services. The collector prompts for a password and creates CE data. In BloodHound, open Administration → Data Collection → File Ingest, upload the output, and wait for processing.

### If something goes wrong

- Legacy bloodhound-python and CE collectors use different schemas. Renaming or zipping legacy JSON does not convert it. CE supports its compatible JSON or ZIP output.
- DCOnly collects directory data; missing session edges are expected.
- If startup or ingestion fails, use the dedicated guide below before reinstalling or resetting anything.

### Confirm and record

- [ ] Open BloodHound and sign in.
- [ ] Confirm ingestion completed and search for your domain or account.

## 7 Read BloodHound relationships

Turn a graph result into a specific, testable question.

### Before you start

- Successfully ingested data in BloodHound CE.
- Your domain username. Run the query in BloodHound Cypher search.

### Find direct group memberships for your account

```cypher
MATCH p = (u:User {name: {{principal}}})-[:MemberOf]->(g:Group)
RETURN p
LIMIT 50
```

### What a useful result looks like

A table or graph shows up to 50 direct memberships. An empty result can mean a different account name, missing data, or no matching edges; this query does not expand nested membership.

### If something goes wrong

- Check the account name on its node and the collection time.
- Graph edges represent observed relationships, not proof that every path is usable now.
- For nested groups, ACLs, sessions, and trust paths, use the query library and verify prerequisites in the associated lesson.

## 8 Map domain trusts

Record trust direction and boundaries before interpreting cross-domain paths.

### Before you start

- A domain-connected Windows PowerShell session with the ActiveDirectory module (RSAT).
- An account permitted to query the domain.

### List trusts from the current domain

```powershell
Import-Module ActiveDirectory
Get-ADTrust -Filter * | Select-Object Source,Target,Direction,TrustType,ForestTransitive
```

### What a useful result looks like

Trust objects show the source, target, and direction relative to the queried domain. An empty result is not proof that your entire lab contains only one domain.

### If something goes wrong

- If the module is missing, use the existing trust lesson for another enumeration method.
- Trust direction alone does not establish access. Check group membership, filtering, selective authentication, and actual permissions.

## 9 Check access through a pivot

Separate routing, DNS, and service reachability when moving into an internal lab network.

### Before you start

- A pivot already set up using your Ligolo or other tunnel notes.
- An internal target and DC address. These checks assume a routed tunnel such as Ligolo.

### Inspect the target route

```bash
ip route get {{target}}
```

### Test a few AD TCP ports through the route

```bash
nmap -sT -Pn -p 88,389,445 {{target}}
```

### Test internal DNS directly

```bash
dig @{{dcIp}} {{dcHost}} A
```

### What a useful result looks like

The route should use the intended tunnel. Port states help separate service access from DNS. A successful TCP check does not prove UDP or every AD collection method works.

### If something goes wrong

- A SOCKS-only setup needs its own client configuration; these direct commands do not automatically use a SOCKS proxy.
- An overlapping local subnet can send traffic to the wrong interface.
- If the route works but DNS fails, check DNS transport and the tunnel capabilities in the pivot reference.

### Confirm and record

- [ ] Record the tunnel, internal subnet, and chosen route.
- [ ] Confirm DNS and the required service before collecting again.
